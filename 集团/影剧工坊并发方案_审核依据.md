## 一、官方事实（一手来源）

### 1.1 MiniMax H3 是什么（GitHub 官方仓库 `MiniMax-AI/MiniMax-H3`）

- **定位**：**开源权重的全模态生成模型**（视频生成，含原生立体声音频）✓
- **开源起始**：2026-07-30 建仓；Stars ≈ 9,797 / Forks ≈ 733
- **输出规格**：时长 **4–15 秒**｜默认短边 **768p**｜**24 FPS**｜音频 **32kHz 立体声**｜支持 21:9 / 16:9 / 4:3 / 1:1 / 3:4 / 9:16
- **权重规模**：**33B 参数**（H3-Omni-Transformer，密集单流）+ **text encoder = Qwen3-VL-32B 完整预训练权重**
- **精度**：两个 checkpoint 均为 **BF16**
- **许可证**：**MiniMax H3 Community License**（⚠️ **含地域条款** —— 有资料称排除美国/欧盟/英国/韩国，**需核验原文再用于商用判断**）

### 1.2 ⚠️ 开源版**只开了 H3-Base**（这条对"能力边界"极重要）

官方明确：完整系统是 **三段**：

| 模块 | 作用 | 开源情况 |
|---|---|---|
| **H3-Context-IR** | 多模态指令理解 / 预处理编排 | ❌ **未开源**（只能调官方 API）|
| **H3-Base** | 生成 768p 视频+音频 | ✅ **已开源**（本次发布的全部）|
| **H3-Regenerate-2K** | 768p 二次生成到 2K | ❌ **未开源**（只能调官方 API）|

→ **结论**：**本地部署只能出 768p**；**要 2K 必须调 MiniMax 官方 API（付费）**。**审核时必须确认他们的方案有没有把这个算进去。**

### 1.3 官方推荐的推理框架（四个）

| 框架 | 官方定位 | 并发适用性（小南判断）|
|---|---|---|
| **SGLang** | **官方示例首选**（cookbook 最全）| ✅ **推理服务框架**，有 `batching_max_size` / DP |
| **vLLM** | 官方推荐 | ✅ 服务框架 |
| **diffusers** | 官方推荐（研究/轻量）| ⚠️ 非服务框架 |
| **ComfyUI** | 官方也支持（有官方模板）| ❌ **单用户工作流引擎 → 这就是"只能 1 人"的根因** |

**官方 SGLang 示例命令（多卡）**：
```
sglang serve --model-path MiniMaxAI/MiniMax-H3 \
  --num-gpus 4 --ulysses-degree 4 \
  --performance-mode speed --host 0.0.0.0 --port 30010 \
  --model-variant fl2va
# ref2va 用 30011 端口，同参数换 --model-variant ref2va
```

## 三、并发的技术手段（SGLang 层）

官方 Cookbook 里出现的并发相关概念：

| 概念 | 含义 | 备注 |
|---|---|---|
| `batching_max_size` | 批大小上限 | Cookbook 的单请求测试用的是 `1` |
| **DP（data parallel）** | 数据并行 —— **多请求吞吐部署用这个** | "多请求吞吐部署请用 picker 的 DP 选项" |
| **TP2 / Ulysses-N** | 张量并行度 | 2 卡用 TP2；官方示例 4 卡用 Ulysses 4 |
| **layerwise offload** | 层内卸载（省显存，掉速度）| 单卡 24G 能跑的关键 |
| **Cache-DiT / AdaLN cache** | 缓存加速 | 有 `build_minimax_h3_adaln_cache` 工具 |
| **replicate** | 复制额外实例 | ⚠️ "batch size 1 时 replicate 多花约 40GB 峰值显存且无延迟收益" |

**→ 审核要点**：**他们的方案必须说清楚用哪种手段（DP？多实例？队列？）以及为什么选它。**

### 7.3 ⚠️ L20 能不能扛 H3（审核要点，小南 10-13 判定）

| | L20 48G | RTX 5090 32G |
|---|---|---|
| 显存/卡 | **48GB**（优）| 32GB |
| 带宽 | 864 GB/s | **1.79 TB/s**（优）|
| FP32 | 59.35 TFLOPS | **104.8 TFLOPS**（优）|
| Tensor 半精 | 119.5 TFLOPS | **210 TFLOPS**（优）|
| 功耗 | **275W**（优）| 575W |
| 定位 | **推理服务卡**（多实例/并发优先）| 消费旗舰（单任务快）|

**H3 权重体量**：33B（H3-Omni-Transformer）**+** Qwen3-VL-32B 编码器，**BF16 共 ≈130GB** → **2×L20 = 96GB 装不下**，官方单卡 24G 案例也是靠 **layerwise offload** 才跑起来。
**→ 审核结论（可引）**：**"2×L20 撑 10 人并发"的说法站不住的风险很高** —— 显存不足 → 必然卸载/换页 → 单位耗时上升 → 并发更差。**除非他们有 96GB 显存下的压测数据。**
**→ 对照**：公开参照里 **256GB（8×5090 整机）才有"十余人同步"的报道**（§5.6 C）。
