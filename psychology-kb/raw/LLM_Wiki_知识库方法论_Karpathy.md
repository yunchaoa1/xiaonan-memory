# LLM Wiki 知识库方法论（2026-06-02 摄入）

> 来源：B站视频，讲解 Karpathy（OpenAI 前科学家）关于个人知识库的正确搭建方式
> 视频时长：3分50秒

## 核心观点

放弃 RAG，LLM Wiki 才是个人知识库的正确方向。

## RAG 的三个本质缺陷

1. 没有知识积累 — 每次查询都是临时拼凑，LLM 不会真正学会任何东西
2. 跨文档推理很弱 — 向量检索按相似度召回零散段落，跨文档综合推理时逻辑容易断裂
3. 工程链路太重 — 向量库、chunk 大小、重排序，个人维护成本极高

## LLM Wiki 核心理念

把 LLM 当成**编译器**而不是临时检索工具：让它一次性把原始资料编译成结构化、可维护的知识库，后续反复复用。

## 系统结构（极简三目录）

| 目录 | 用途 | 规则 |
|------|------|------|
| raw | 存放原始资料 | 只进不出，知识的源头 |
| wiki | LLM 自动维护的结构化知识库 | 全部 Markdown 文件 |
| prompts | 存放模板和提示词 | 规范生成逻辑 |

## 四步工作流

1. **Ingest（导入）** — 看到好文章直接丢进 raw，不用手动分类，越快越好
2. **Compile（编译）** — LLM 读取新内容，自动提炼关键概念、撰写词条、建立页面间链接、更新总索引。只做一次，后续反复复用
3. **Query（查询）** — 提问时直接从 wiki 读取结构化内容回答，不再反复扫描原始文档
4. **Audit（自检）** — 定期让 LLM 扫描整个 wiki，自动处理信息不一致、孤立页面、过时内容

## 对比 RAG

| 维度 | RAG | LLM Wiki |
|------|-----|----------|
| 知识积累 | 每次临时拼凑 | 持续沉淀，形成复利 |
| 可读性 | 黑箱向量库 | 全 Markdown 透明 |
| 工程复杂度 | 向量库 + 重排序 | 文件夹 + LLM |
| 跨文档推理 | 碎片召回，容易断裂 | 结构化，上下文连贯 |
| 个人可落地性 | 较重，成本高 | 极轻，开箱即用 |

## Karpathy 工具栈

- 本地文件夹存储 raw 和 wiki
- Obsidian 作为知识 IDE（反向链接、知识图谱、DataView 查询）
- LLM：Claude Opus 等大上下文模型
- Git 做版本管理，记录所有 wiki 修改

## 典型一日流程

网页剪藏 → 存入 raw → 执行编译 → 更新 wiki → 从 wiki 直接获取答案 → 把好的解释保存为新词条 → 定期自检修复

## 一句话总结

Obsidian 是知识 IDE，LLM 是程序员，Wiki 是代码库。不需要花里胡哨的技术，只需要一个持续生长的知识体系。
