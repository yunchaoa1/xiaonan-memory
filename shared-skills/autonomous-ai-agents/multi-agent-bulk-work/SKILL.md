# 多子代理大批量作业

## When to Use

任一条件成立就用本技能：

- 一次要改或产 **20 份以上文件**（提示词、分镜、剧集、文档章节）
- 缺陷形态是**「看起来很对但缺东西」**——不是语法错、不是跑不起来，是"少了该有的东西"
- 用户抱怨过同一批产物**反复返工**
- 要判断"这批活儿干完了没有"，而产物数量多到没法逐个肉眼过

不适用：单份文件修补（直接改）、纯机械转换（用脚本）、需要用户现场指挥的任务（子代理问不了问题）。

## 核心结论（2026-11-23 实战验证）

**写的人和查的人必须分开。** 自己写完自己说"过了"，缺陷永远漏——因为检查者和生产者是同一个判断。

**改之前先把规则源读全**：规则通常散在 `SKILL.md` + `references/` + `checklist` 里。只读主文件就开工 = 用了 1/6，结果跟不用差不多。详见 `references/read-the-rules-first.md`。

## 三段分工（顺序不能反）

```
① 审（1-2 个）      只挑毛病，禁止改文件，输出「缺什么 → 补什么」
② 设计（1 个）      整体层面（节奏曲线、结构），不是逐段打补丁
③ 改（每 5 份一个）  并行，各写各的，输出到 new/ 目录，不覆盖原稿
④ 验收（我自己）     不甩手，三件套逐项跑
```

**① 审** — 给它硬数据锚点（如"20 份里 13 份零动作、某词用了 11 次"），让它对着规则源逐条比。提示里必须写**"绝对不要修改任何文件"**，并要求输出**可直接粘贴的句子**，不许只写"建议加强"。

**② 设计** — 治的是**整体病**（节奏平、高潮突兀、密度不对），逐段打补丁治不了。要求带数值的曲线（每份 1-10 分）+ 具体到"第几份第几处"的落点。**把它和①的结论交叉比对：两个独立结论指向同一处，那处就是真病灶。**

**③ 改** — 每个必须收到三样：诊断清单（补什么）、整体曲线（这份该多大强度）、硬边界（只改允许改的部分，不许动原文/字段结构/编号）。原稿一律不动，**写到 `<原目录>/new/`**。

**④ 验收** — 见下节，必须自己做。

## 验收三件套（不信自报）

**实测教训：4 个子代理全部自报「通过 / FAIL 0」，实际 5/20 份没过机检。**
两个原因：①子代理只跑了自己那批的部分检查；②有一个撞了迭代上限（`TRUNCATED`），照样列了 5 个"已完成"文件。

1. **产物存在** — `ls new/ | wc -l` == 预期份数。
2. **内容没被偷改** — 正则提取受保护内容（台词、编号、关键字段），逐份和原稿比对，输出"新旧各 N 条，不一致 0 份"。**这是最容易被顺手改掉的地方，也是用户最不能忍的。**
3. **机检真过** — 全量跑，`FAIL` 清零。WARN 可留（但要能逐条解释），FAIL 一个都不许留。
4. **改完必须全量重跑** — 修一处不能只验那一份，补内容常把别处顶超限。

## 踩过的坑

| 现象 | 真因 | 处理 |
|---|---|---|
| 子代理说全绿，实际 FAIL | 只跑了自己那部分检查 | 全量重跑，不认自报 |
| `TRUNCATED: hit max_iterations` 但仍列"已完成" | 撞迭代上限 | 单独重验那批，缺的只补那几份 |
| 改完 FAIL 反而变多 | 补的内容顶超单条词数上限 | 删修饰词压回，保留核心描述 |
| 报"命中否定词"，但那词在台词标签内 | 头与正文之间用了句号没分号，机检分不清哪是正文 | 统一改分号：`[识别头] 描述; 正文` |
| 加片后时长超上限 | 没回头压缩时间戳 | 尾部几处时间戳前移，或合并 |

## 派工模板（每份都要写清）

```
你的份：XX-XX
必读：<规则源路径列表>（用 read_file 实际读，不许凭记忆）
诊断：<缺口清单，含可直接粘贴的句子>
强度：<该多大，为什么>
边界：不改原文/不改字段结构/不改编号/写到 new/ 不覆盖原稿
交付：绝对路径列表 + 自检命令的真实输出
```

## 用户视角

用户要的是"别再返工"，不是"这次很努力"。所以：
- 汇报时报**三关结果**（原文没改 / 机检清零 / 关键指标前后对比），不要只报"已完成"
- 中途抓出的问题要主动说（"5 份不合格，全是我自己的格式问题，已修"），这比"全部通过"更让人信
