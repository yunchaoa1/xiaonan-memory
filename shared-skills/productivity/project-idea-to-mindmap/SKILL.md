# 项目思路 → 脑图（从想法到结构化方案）

## When to Use（何时加载）

- 凡哥说「**我有个新项目想法**」「**接了个单，怎么落地**」「**这个项目该怎么做**」「**帮我想想**」
- 要对一个新项目做**结构化思考**，并**产出脑图**
- 凡哥给一份需求文档/客户资料，要理成"能开工的方案"

## 先分清分工（别搞混，也别重复造轮子）

| 技能 | 管什么 | 阶段 |
|---|---|---|
| **本技能** | **从 0 到 1：把"想法"变成"结构化思路"**（想清楚） | **想** |
| `project-topology-diagrams` | **画图工具链**（XMind 直出 / draw.io）+ **已有项目的进度更新** | **画** |
| `creative-project-structure` | **创作类**项目的组织（世界观 / 角色 / 剧情） | 创作 |

> 别一上来就画图 —— **没想清楚就画 = 画出一张好看的废话。**

## ⚖️ 权威底座（2026-10-11 补课 —— 原版是我自己合成的，凡哥质疑后校准）

> **诚实说明**：下面那套"四层"是我按理解把三家 AI 圈来源**综合**出来的，**不是任何权威标准本身**。
> 凡哥追问「**有没有社区里非常靠谱的方式方法**」→ 补上**行业标准**，每条都能查到原始出处。**以后以这三个底座为准，"四层"只是它们的操作化版本。**

### 底座 1 · 范围与拆解 = **WBS**（PMI / PMBOK 标准；我们的拓扑图早就在用）

**权威定义**：WBS = "**面向交付物（deliverable-oriented）的层级分解**"，PMBOK 核心工具。

**三条不可违背的规则**
1. **100% 规则**：WBS 含**项目范围的 100%**；**子层级之和必须 = 父层级的 100%**；**不含范围外的工作**（不能超 100%）
2. **MECE**：**相互独立**（不重叠）+ **完全穷尽**（不遗漏）
3. **写名词不写动词**：WBS 回答"**做什么（what）**"，**不写**"何时/谁（when/who）"——那是排期表的事

**三级分解法**

| 级 | 拆到哪 | 硬标准 |
|---|---|---|
| 一级 | **可交付成果** | **必须可验证的实物** —— ✗"提高性能" ✓"性能测试报告" |
| 二级 | **工作包** | **一个团队 2—4 周**能完成 |
| 三级 | **活动任务** | **一个人几天**内完成 |

**拆完自检五问**：可理解？可分配？**可估算**？可跟踪？可交付？

**三个经典错误**（MECE 检查会抓出来）
- ✗ 按**部门**拆（前端/后端/测试）→ 同一功能被割裂到不同部门
- ✗ 按**时间**拆（第一周/第二周）→ 那是排期，不是分解
- ✗ 按**人员**拆 → 混淆"工作内容"与"资源分配"（内容稳定，资源会变）
- ✅ 正解：**一切以"交付成果"为导向**

**两条实用技巧**：① 留「**未知工作包（占位）**」——承认未知，别假装都清楚；② **别过度分解** —— 拆到"一个人几天能完成"就停（拆到小时级 = 管理成本 > 执行成本）。

### 底座 2 · 架构 = **C4 模型**（Simon Brown，被称为"代码的 Google 地图"）

**核心思想**：架构用**四层缩放**表达，**不同受众看不同层**（像地图的广角/标准/长焦/微距）。

| 层 | 图 | 给谁看 | 画什么 |
|---|---|---|---|
| **L1** | **系统上下文图** | 非技术人 / 老板 | 本系统 + 用户 + **所有外部系统**（= 对外边界）|
| **L2** | **容器图** | 技术主管 | 应用 / 数据存储 / 微服务（**可独立部署的单元**）|
| **L3** | **组件图** | 开发 | 容器内部由哪些组件构成 |
| **L4** | **代码图**（可选） | 开发 | 类 / 接口（用 UML / ERD，**多数项目不必画**）|

**每张图的硬要求**：**标题 + 图例**必须齐；每个元素标明**名称 / 类型 / 技术选择 / 一句描述**（别让图有歧义）。
**支持性图**（按需）：系统景观图（多系统全景）、**动态图**（一次请求怎么流经各组件）、**部署图**（跑在哪台机器上）。

### 底座 3 · 架构文档结构 = **arc42**（可选，与 C4 天然配套）

标准章节顺序：**业务上下文 → 技术上下文 → 解决方案策略 → 构建块视图 → 运行时视图 → 部署视图**
映射关系：arc42 的 *Context and Scope* ↔ C4 **L1**；*Building Block View* 的 L1/L2/L3 ↔ C4 **L2/L3/L4**。

## 四层操作版（把上面三个标准落到"能直接干的活"）

### 第 1 层 · 需求（想清楚"做什么"）

- **目标用户是谁**？（自己用 / 团队用 / 卖给客户 / 多租户）
- **核心功能只要 3—5 个** —— 超过 5 个就是没想清楚
- **成功标准必须可度量**：✗"要快" ✓"**100ms 内**"；✗"好用" ✓"**3 步内完成**"
- 每个功能写**用户故事**：`作为<角色>，我要<功能>，以便<好处>`

### 第 2 层 · 架构（想清楚"怎么搭"）—— **最容易被跳过的一层**

- **系统组件**：有哪些模块/服务，各自负责什么
- **数据流**：数据从哪来 → 经过谁 → 到哪去（**不画数据流，问题一定在后头爆**）
- **集成点**：外部 API / 服务 / 数据库 / 账号 —— **隐藏的集成点是最大的坑**
- **边界**：明确写出「**做什么 / 不做什么**」（防范围蔓延）
- **约束**：技术 / 资源 / 时间

### 第 3 层 · 任务（想清楚"怎么干"）

- **分层**：阶段 → 任务 → 子任务
- **粒度**：**每个任务 1—4 小时**，更大就继续拆
- **依赖**：谁必须先做完
- **并行标记**：哪些能同时干
- **AFK / HITL 标记**：哪些我能自动做、哪些**必须凡哥**（账号/密钥/决策/发布）

### 第 4 层 · 风险（想清楚"哪里会翻车"）

- 分三类：**技术风险 / 依赖风险 / 时间风险**
- 每个风险配**一句缓解动作**（不是"注意一下"）
- 标出**关键路径**（最长的依赖链）+ **留 15—20% 缓冲**（别拍满工期）

## 问对问题（复用我们已跑通的"落地方案四问"格式：每组附我的默认答案，凡哥回"对/改"）

| 组 | 问什么 |
|---|---|
| **A 边界与钱** | 只做哪部分？资金/数据怎么流？一次性还是持续？ |
| **B 角色与闭环** | 谁用？各角色做什么？闭环是什么（货怎么走/钱怎么走/数据怎么走）？ |
| **C 内容与合规** | 形态？素材来源？谁审？ |
| **D 时间与人力** | 里程碑？要不要排期？→ ⚠️ **人力分配与 5 人怎么分不由小南定**（凡哥 2026-10-10 明确） |

## 落到脑图（照凡哥的定稿标准）

- **一级只放 3—4 条**（核心思路 / 业务闭环 / 模块 / 内容支线）
- **从左到右展开**（`org.xmind.ui.logic.right`）
- **零专业术语、人话**（跑 BAN 词黑名单自检，命中必须 0）
- **未定口径**单独一个「待确认（请凡哥拍）」分支，**不自行增补**
- 工具与命令：见 `project-topology-diagrams`（`xmind_writer.py` 直出 `.xmind`，不用开 XMind）

## 五个坑（来自社区实战，别踩）

1. ❌ **跳过架构直接写需求** → 集成点后期才暴露，返工
2. ❌ **验收标准模糊**（"用户友好""高性能"）→ 无法验证，等于没写
3. ❌ **边界不写清** → 范围蔓延，工期失控
4. ❌ **缺数据流分析** → 问题暴露太晚
5. ✅ **接口优先**：先定组件之间的"契约"，再填内部实现
