# 第三方 AI（豆包/飞书）共享记忆文件

用途：非 Hermes 的外部 AI（凡哥手机/飞书里的豆包）也在积累工作记忆，需要并进小南的总控台。
结论来自 2026-09-15 跟凡哥来回四轮才定案，**别再自己发明中间层**。

## 定案机制：一个共享文件 + 按需读取

```
D:\Hermes\xiaonan-memory\集团\豆包工作记忆.md      ← 唯一通道（在 git 仓库内，两端实例都能看到）
```

**三区结构（必须保持）**

| 区 | 谁维护 | 内容 |
|---|---|---|
| **A 区 · 现状口径** | 小南维护，**豆包只读** | 项目总览 / 结束定义 / 已确认决定（带日期）/ 术语统一 |
| **B 区 · 豆包写入** | 豆包追加（每条带日期） | [新增/变更/决定/卡点] ｜内容 ｜来源 |
| **C 区 · 变更日志** | 小南维护 | 谁哪天改了什么 |

**小南的动作**：读 B 区未并入条目 → 凡哥确认过的并入 `DASHBOARD.md` / `dashboard-tree.html`（const DATA）→ 在 B 区该条行尾标 `→ 已并入 YYYY-MM-DD` → 结论补进 A 区（A 区永远＝当前有效口径）。

**读的时机（凡哥 2026-09-15 定：按需读取）**：① 每次开工读 DASHBOARD 时 ② 凡哥提到项目/考核/进展/豆包时 ③ 要汇报或更新总控台时 ④ 凡哥说"同步一下"。
**读法**：`python D:\Hermes\scripts\doubao_memory_watch.py` → 只列出 B 区**未并入**条目（`NO_NEW_ENTRIES` = 没有新东西）。

## ⛔ 两个被凡哥否掉的方案（不要再提）

1. **定时巡检（每分钟/每 30 分钟）**：凡哥原话「我是说豆包直接把记忆传给你，你干嘛还要每 30 分钟检查一次呢？」→ 他要的是不需要中间层的按需读取；**巡检任务已删除**。
2. **飞书消息当中间线**：网关能收飞书消息从而秒级唤醒小南，但凡哥否掉——**不设中间环节**。

→ 教训：**"全自动"在凡哥语汇里 ≈ "我不要多做任何动作"，不等于"你必须后台常驻轮询"。** 方案设计前先把这两种理解摆出来问一句，别自己选。

## 铁律

1. **外部 AI 只能写共享文件，不能直接写小南的持久记忆**：`MEMORY.md` 有 **2200 字硬上限**（每轮对话都注入，塞爆后小南**什么都存不进去**）。外部 AI 写共享文件（不限字数），小南负责**压缩**进记忆/总控台。用"抽屉只有 2200 字"这种说法跟凡哥解释，他一次就懂。
2. **总控台只认凡哥确认过的口径**：豆包块里属于**推测**的一律只进"待确认（外部输入）"，**不得写进真相源**（凡哥反复强调"别把总控台搞乱"）。
3. **每条带来源 + 日期**（豆包 / 凡哥 / 小南，YYYY-MM-DD）；叫法冲突**以凡哥口径为准**，并在总控台记一条"口径统一"。
4. 需要凡哥拍板的，**在聊天里用普通提问问**（不用 clarify 提问卡），别塞进文件等他看。
