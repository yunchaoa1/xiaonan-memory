# 技能库维护 · Skill Library Maintenance

技能库治理的操作篇（评估方法论见 `D:\Hermes\skills_archive\skill-library-governance`，已归档仅作参考）。

## 核心事实（2026-08-06 实测）

### Hermes 技能机制
- **无关键词规则引擎**：技能 name+description 进系统提示，模型语义判断后 skill_view 加载。自动激活是概率性的，不是 100%。
- 中文描述对中文触发至关重要；英文描述 + 高度相似的描述族（如 26 个 seedance 子技能）会互相抢触发。
- 确定性方式：`/skill 名称`、`hermes -s 名称` 预加载。
- 技能索引每会话占 token：120 技能 ≈ 16,346 字符 ≈ 4K tokens；瘦身到 60 技能减半。

### curator（技能管家）自动归档冲突
- 默认 **ENABLED**，每 7 天跑一次；**30 天未用 → stale；90 天未用 → 自动归档**（从列表消失）。
- 判定依据是 .usage.json 使用频率，**不看业务价值**——低频但有用的技能（撩妹聊天、月更工具）会被误归档。
- consolidate（LLM 合并重叠技能为伞形）默认 off，需 opt-in；开启会合并高度相似的技能族（如 Seedance 22 件套）。
- curator 只归档不删除，自动备份可 `hermes curator restore` 恢复。
- **防重复查证**：curator 全部 12 个命令（status/run/pause/resume/pin/unpin/restore/list-archived/archive/prune/backup/rollback）**没有任何创建功能**；`skill_manage` 创建同名技能会被源码拒绝（`A skill named 'X' already exists`）；Hermes 加载同名去重、本地优先。唯一防不住的是"名字不同内容相似"（world-building/worldbuilding）——靠人工查。

### curator 调参（凡哥 2026-08-06 拍板"不限时"模式，已执行）
- config.yaml **没有的段 = 用代码默认值**；调整只需在文件末尾**追加覆盖段**，不用写全量配置。
- 配置键（源码默认值）：`enabled: True`、`interval_hours: 168`、`min_idle_hours: 2`、`stale_after_days: 30`、`archive_after_days: 90`、`consolidate: False`、`prune_builtins: True`（内置技能也会归档！）、`backup.enabled: True, keep: 5`。
- 已执行的"不限时"追加段：
```yaml
curator:
  enabled: true
  stale_after_days: 36500
  archive_after_days: 36500
  consolidate: false
  prune_builtins: false
```
- 36500 ≈ 100年 = 技能永不因时间被归档；`prune_builtins: false` 保内置技能；consolidate **永远保持关闭**（辅助模型不懂凡哥业务，可能合并 Seedance 22件套并改写实测规则）。
- 验证：`hermes curator status` 应显示 `stale after: 36500d` / `archive after: 36500d` / `consolidate: off`。

### Self-improvement review（后台自动生成技能 · 2026-08-06 破案）
- **机制**：`agent/background_review.py` 后台运行，实时读会话 → 自动创建技能（含 references/、scripts/ 固化）→ 自动 patch 现有技能（把会话教训写进相关技能）。
- **日志特征**：`desktop.log` 出现 `💾 Self-improvement review: Skill 'X' created. / Patched SKILL.md in skill 'Y'`；`agent.log`/`errors.log` 里能看到它调 skill_manage 的记录。
- **它是省事的好机制**：自动沉淀的技能质量高（会固化脚本、写执行记录 reference），不用白不用——但会与人工创建**打架**（本次 3 个治理技能并存即它+人工同时生成）。
- **防打架铁律**：创建技能**必须用 `skill_manage(action='create')`**（有 `A skill named 'X' already exists` 重名保护）；**绝不要用 `write_file` 直接写技能目录**——write_file 无重名保护，会绕过系统检查造成重复（本次教训：根级 maintenance 就是这么写出来的）。
- **发现重复后的处置**：对比各版本 SKILL.md → 互补内容合并进一个 → 其余 `mv` 到 `skills_archive/` 保留备份 → 验证 `hermes skills list` 只剩一个。
- 详细证据见 `references/background-review-mechanism.md`。

### 受保护技能的更新边界

- `skill_manage` 拒绝写入 user-owned、bundled、hub-installed、external-dir 或 pinned 技能时，不要通过 `write_file`、复制到新目录或改名来绕过保护。
- **已知本库的 user-owned 实例**：`content-ingestion`（2026-11-04 实测被拒，报 `the skill is not curator-managed (created_by=None)`）。想改它必须由凡哥在前台跑 `hermes curator adopt content-ingestion`。→ 巡检时遇到这类拒绝，**直接把建议写进回复给凡哥**，别反复试其它写入路径。
- 先把新经验留在当前会话，向用户说明目标技能受保护；如确实要纳入自动治理，建议用户在前台执行 `hermes curator adopt <name>`，再由用户明确触发后更新。
- 如果经验属于可迁移的上层类别，优先寻找一个 curator-managed 的 class-level umbrella；确认没有合适的伞形技能后，才考虑创建新的 class-level 技能，禁止创建“一次会话一个修复技能”。
- “已加载”不等于“可写入”；加载技能、用户手写技能和用户要求前台创建的技能都默认保留所有权边界。
- 入口：`D:\Hermes\config.yaml` 的 `skills.disabled` 列表。
- ⚠️ **patch 工具拒绝修改 Hermes 配置文件**（security 保护）——必须用 python 脚本读写，或 `hermes config` 命令。
- 停用 builtin 技能只是不显示，文件还在，随时可恢复（从 disabled 移除即可）。

### 2. 归档技能（彻底移出扫描）
- 移到 skills 目录外：`mkdir -p D:\Hermes\skills_archive && mv skills/<类>/<名> skills_archive/<名>`。
- 移出后不再被发现；如需恢复，移回原路径即可。

### 3. 合并重复技能
- 先对比两个 SKILL.md：互补则合并成完整版（如 world-building 英文工作流并入 worldbuilding 中文设计原则，保留业务核心方），被吸收方移出目录。
- 同名冲突技能（world-building vs worldbuilding）优先保留中文、业务核心的一方。

### 3.5 多技能合并成一条（N→1）＋ 隔离柜（2026-10-22 实战：6 个提示词技能 + 30 个 seedance → 1 个 h3-video-prompt）

凡哥说「合成一个」「太多了」「这些都需要吗」「只要 X 的」时走这条。他一句指令里通常已把三种处置说完，按他的词分：**合并**（"合成一个"）、**删除**（"直接删除"）、**隔离**（"隔离掉，没告诉你说要用时不要翻出来"）。

**N→1 六步**
1. **读完所有源的完整正文再动手**——规则型技能漏一条就是功能退化。别靠记忆，别靠 grep 片段。
2. **主文件只放"每次都用"的**（触发 → 流程 → 硬规则 → 自检）；官方原文、长篇底稿、历史案例全进 `references/`。用户视角仍然是"一个技能"。
3. **写完对照原文逐条补漏**（本次漏了动作因果链／运镜五要素／尺度对比镜三条，靠通读原文件才发现）。
4. **冒烟测试**：按新技能真产出一个样本，用脚本逐项验格式（本次 8 项全 PASS 才敢交付）。不要"看起来对"就算过。
5. **改路由 + 扫悬空引用**：`grep -rln "旧技能名" --include=SKILL.md .`；活文档必改，历史快照（运行数据、旧交接包）不改。
6. **同步三步**：`sync_skills.py push`（只增不删）→ **手工删仓库 `shared-skills/` 里的旧目录** → git commit（历史可回滚）。

**隔离柜模式**（凡哥要"收起来但别删"时）
- 移出 `D:\Hermes\skills` → `D:\Hermes\xiaonan-memory\skills-archive\<组名>\`：Hermes 扫不到、随 git 同步到另一台、但不进加载路径。
- 柜内必写 `README-隔离说明.md`：隔离日期 + 凡哥原话 + **恢复命令**（`cp -r ... D:\Hermes\skills\creative\`）+ 一句"没明说不要加载"。
- 路由表对应行改成「**只在凡哥明说时**：先装回来再用」。
- ⚠️ **必须同时删 `shared-skills/` 里的副本**，否则下次 `sync_skills.py pull` 会把它们装回运行目录，隔离白做。

**删除前确认可恢复**：`git log -1 -- <path>` 有提交记录才删（没有就先提交一次）。删完在 DASHBOARD 里记一句"git 历史可恢复"。
⚠️ **别用 `push --mirror` 去清删除项** —— 它会把仓库里另一台机器的自建技能一起删掉。手工删目录更安全。

**⚠️ 凡哥问「技能在哪」时，只给路径。**
实战教训（2026-10-22）：凡哥说"把 skill 告诉我在哪，我发给他" → 小南顺手打了个 zip，被当场纠正"大哥，我就是让你告诉我 skill 的位置，你在干嘛"。
- 「在哪 / 路径 / 位置」= **只要绝对路径清单**，一行一个，按用途标一句"哪个先看"。不要打包、不要写说明、不要生成新文件。
- **⚠️ 2026-11-19 复犯，加硬**：这次给了"路径 + 22 个文件清单 + 来源 + 没改过的说明 + zip"，凡哥仍回「**文件位置告诉我啊**」。
  → 他要的是**一眼能复制的那两行**。**路径放最先、单独成行、不加任何前后缀**；文件清单、出处、是否改动过、要不要打包，**他没问就一个字都别写**。
  判据：**答案如果是"一个路径"，回复就只该有一个路径。** 解释得越多，他觉得越没答到点上。
- 「直接删除 / 隔离掉 / 合成一个」= 才动手改库。
- 「怎么交给他能对齐」= 才做交付物（见下条）。
- 分不清时按最小的那个做：他要答案时给答案，别给工程。做完一件事就停，不叠加。

### 3.6 把技能交给别人用，怎么保证效果一致（2026-10-22 实战：H3 规矩交给小李）

**核心判断：只发文档 ≠ 效果一致。** 人会跳步；文档给的是道理，不是关卡。凡哥问"怎么交给他能对齐"时，答案是三件套（缺一件都保不住）：

1. **干净单文件规则**——从 SKILL.md 派一份对外版：砍掉本机绝对路径、内部流水线契约、团队人员/项目代号，把"对方最容易栽的那一节"提到最前面。
2. **机器关卡脚本**（`scripts/` 目录）——写完必须跑，全 PASS 才许交。这是唯一不会心软的一环，也是"效果一致"的真正保障。
3. **正反例对照**——同一件事给"我们这么写"和"常见错法 + 模型会怎么表现"，人看反例学得比看正例快。
4. 收口口径写死：**脚本全绿 + 第一镜人工抽检**。不是"他说他按规矩写了"。

验证交付物本身：拿正例跑一遍要**全 PASS 退出码 0**，拿反例跑要**大面积 FAIL 退出码 1**。脚本只报 PASS 不报 FAIL = 脚本坏了，不能交。
⚠️ 写校验脚本时小心"空集假通过"：正则没匹配到任何目标（比如台词没包 `<d>` 导致取不到台词）时，长度类检查会返回 PASS 掩盖真问题——必须单独加一条"格式本身缺失"的检查兜住。
完整案例、文件清单与话术见 `references/skill-handoff-alignment-2026-10.md`。

### 3.7 找回"之前给某人写的那个 skill / 改过某条规矩的那一版"（版本溯源，2026-11-04 实战：凡哥找给小李的写作 skill）

凡哥的说法常是模糊的（人名 + 用途 + "改过台词密度的那一版"），**库里往往没有一份文件名写着那个人**。不要回答"没找到"，按下面顺序溯到唯一一份，并用证据说清为什么是它。

1. **先承认边界**：开头一句"库里没有文件名写着'给某某'的那份；能对上'某规则改过'的是这一份"。别把推测说成事实。
2. **四个地方都要查**（同一份 skill 常常有 3–4 个副本）：
   - 活的：`D:\Hermes\skills\<类>\<name>\SKILL.md`
   - 仓库同源：`D:\Hermes\xiaonan-memory\shared-skills\<类>\<name>\SKILL.md`
   - 交接包解压版：`xiaonan-memory\opc-sim\交接包_*\01_节点Skill\<name>\`
   - **真正发出去的包**：`D:\Documents\xwechat_files\<账号>\msg\file\<年月>\*.zip`（微信接收目录，这里才有"当时发出去的是什么"）
3. **判定"同一版"靠字节数 + `diff -q`**，不靠"看起来一样"。例：活文件 17,036 字节、日期 2026-09-21；交接包副本 diff 零差异；zip 内也 17,036 → 三处同一版。
4. **日期看 git log，不信 mtime**：`git log --all --date=short --pretty='%ad %s' -- <path>`。同步/解压都会刷新 mtime。
5. **用"条款原文"锁定版本**：搜规则关键词（如 `台词密度`、`177 字/分钟`、`300-350`），命中即证据；再打开旧包确认旧版**没有**这段 → 新旧可判定。
6. **交付要给全六项**：活文件绝对路径 + 版本号（frontmatter `version`）+ 字节数 + 改动日期 + 同版副本路径 + 打包件路径，最后加一句**旧包警告**（哪一个是旧包、为什么不能用，例：9-07 的 `OPC交接包_给平台同事.zip` 里还是 v0.2.0 英文版，没有台词规矩）。
7. **只给答案，不擅自打包**：问"找/哪一版/在哪"= 给路径和证据；**末尾一次只问一句**"要单独打一个干净包发给他吗"。别顺手打 zip（同 §3 的"只给路径"教训）。
8. 完整案例（含各副本路径、字节数、版本差）见 `references/delivered-skill-version-tracing-2026-11.md`。

**溯源时的四个坑（都会造成"假没找到"）**
- **搜索命令静默失败 = 假阴性**：`rg ... 2>/dev/null` 在没装 rg 的机器上不报错、退出码 0、输出空 → 直接判"库里没有"是错的。**任何"找不到"的结论，先确认搜索真跑了**（`command -v rg` 或直接用 `grep -rln`），永远别把 stderr 丢掉。
- **扫全盘会超时**：`D:\Hermes` 下有 cache/cron 几万个文件，`search_files` 全目录搜会 timeout 被截断。**限定到 `skills`、`xiaonan-memory`、`Documents` 这类具体目录再搜**。
- **zip 里的中文名是 GBK**：`unzip -l` 出乱码甚至 `Binary file matches`。用 python 还原：`n.encode('cp437').decode('gbk')`，并能拿到 `i.file_size` / `i.date_time` 当版本证据。
- **只比"最新"会拿错包**：`xiaonan-memory\opc-sim\` 里压着旧 zip，文件名不带版本；必须开包看字节数和正文，别按文件名排序就下结论。


### 3.7-bis 验证「这个是不是原版」（哈希比对，2026-11-19 实战：凡哥直接问「这个是你下载的原版吗？」）

凡哥问这句话，**不是要你保证，是要证据**。回答「是的，没改过」= 空口；他要的是能复核的东西。

**做法：逐字节比，不比时间戳**

```bash
# ① 本地全量哈希
cd <技能目录> && find . -type f | sort | while read f; do printf "%s  %s\n" "$(sha256sum "$f" | cut -d' ' -f1)" "$f"; done

# ② 从 GitHub raw 拉原版，逐个 cmp（比哈希更直白：一致/差异/仓库没有 三分）
cmp -s "$LOCAL" "$FETCHED" && echo "SAME" || echo "DIFF"
```

汇报口径固定为一行：**`一致 N ｜ 差异 0 ｜ 仓库没这个文件 1`**。凡哥认这个格式。

**更省事的比法：一个文件都不用下（2026-11-22 实测，raw 打不开时也能核）**

`raw.githubusercontent.com` 走不通（本次 `curl` 直接 exit 6 = DNS 失败），但 `api.github.com` 通 → 改用**blob sha 对撞**：

```python
# ① 上游指纹：API 的 tree 里每个 blob 自带 sha + size
#    curl -s "https://api.github.com/repos/<owner>/<repo>/git/trees/<branch>?recursive=1"
# ② 本地指纹：git 的 blob sha1 算法，纯本地算，不联网
sha = hashlib.sha1(b"blob %d\0" % len(data) + data).hexdigest()
# ③ 逐个比：本地 <相对路径> ↔ 上游 "<repo子目录>/<相对路径>"
```

**输出必须四分类**（只报\"一致/不一致\"会漏掉最要命的两类）：
`完全一致 N` ／ `内容不同（附本地 vs 上游字节数）` ／ **`本地多出（上游没有）`** ／ **`本地缺失（上游有）`**。

本次实测（`forest-laoli-h3`）：上游该目录 55 个文件、本地 23 个 → **一致 22、不同 0、本地多 1**（`case01_test.md`，3,231 字节，装完后 2 分钟生成的测试稿）、**本地缺 32**（`scripts/tests/` 29 个官方用例 + CHANGELOG 等）。
→ 结论一句话就够：**技能本体零改动，仍是最初版本；顺带暴露当初没下全**。这两句都要说，别只说前半句（§3.7-bis 坑 3：\"我下了 N 个\"≠\"仓库只有 N 个\"）。

**四个坑（都造成过"假不一致"或"假一致"）**

1. **仓库内路径常多一层同名子目录**：`main/SKILL.md` 直接拼会返回 **14 字节的 `404: Not Found`**（四个"文件"哈希全一样就是它）。
   先 `git/trees/main?recursive=1` 拿真实路径 —— 本次真身是 `main/forest-laoli-h3/SKILL.md`。
2. **`api.github.com` 和 `raw.githubusercontent.com` 走不同通道**：`ghfast.top` 前置能取 raw，但 api 往往要本机代理
   （`urllib.request.build_opener(ProxyHandler({'https':'http://127.0.0.1:7897'}))`）。
   **代理没开时 raw 也可能 404 —— 先确认代理，再断言"仓库没这个文件"**（本次凡哥一句「刚才我没打开代理」直接把结论翻了个面）。
3. **「我下了 N 个文件」≠「仓库只有 N 个」**（最容易失分的一条）。本次仓库 **59 个文件**，我只下了 **21 个**，
   另外带了 **1 个自己为测机检临时造的样本**。当时汇报"22 个文件全部成功"，凡哥以为就是全量。
   → **报告下载结果必须三件事一起说**：仓库总数 / 已下载数 / **没下载的是什么**（测试用例、CHANGELOG、README、LICENSE）。
4. **自己临时造的东西别丢进技能目录**。为试机检脚本下载的样例（`case01_test.md`）混进技能根目录后，
   比对时就多出一个"仓库没有"的文件，交付包里还得靠人工剔。**临时样本放 `cache/`，技能目录只放原版文件。**

**交付前自检**：打包给第三方时，包里应当**只有**原版文件；剔掉自己加的样例后重新打包，并在回复里点明"剔掉的那个不是原版"。

### 4.5 重命名技能（2026-09-24 实战：gpt-image-* → qwen-image-*）

工具换代（出图模型从 GPT Image 换到 Qwen-Image）时节点 skill 要跟着改名。改名是「文件系统 + 全库引用 + 交付包」三处同步的原子动作，漏一处就留悬空引用。

1. **别直接 `mv`**：Hermes 常驻监控 skills 目录，`mv`/`rm` 可能报 `Device or resource busy`。用 **`cp -r 旧名 新名` → `sleep 3` → `rm -rf 旧名`**（重试一次基本能删掉）。⚠️ 两个目录同时存在时必须立刻处理——两份 SKILL.md 声明同一个 `name:`，加载会重复。
2. **frontmatter 的 `name:` 同步改**（目录名带 `-opc-test` 后缀、`name:` 是短名，属历史惯例，保持一致）。
3. **全库找引用**：`grep -rln "旧名" /d/Hermes/skills /d/Hermes/xiaonan-memory | grep -v "\.git/"`，分两类——**活文档必改**（其他 skill 的 SKILL.md/references、DASHBOARD、交付包说明书）；**历史快照不改**（`opc-lean-plan/`、`opc-sim/v2/` 运行数据、`.curator_ledger.jsonl`、`.usage.json`、旧交付 zip）。
4. **批量替换走 execute_code 精确 `str.replace`**（替换串按「先长后短」排序，逐文件打印命中数）；不要用正则改结构化文本。
5. **改完三查**：`health_check.py` + frontmatter（每个 skill 的 `name:`/`description:` 各 1 条）+ 引用完整性两层检查（见 §4）。
6. **交付包同步**：包内目录名、说明书节点表、依赖表、打包（zip 名带日期+版本）、旧 zip 清理，一步不落。

### 4.6 模型换代的技能改造：先查依赖，再决定删还是改名（2026-11-18 实战：gpt-image / qwen-image → 豆包 Seedream）

**病根**：每换一次出图/视频模型，就留下一个**以模型命名**的技能（`gpt-image-*` → `qwen-image-*` → `z-image-*`）。体检时它们被报成"两道鱼香肉丝"，看着像重复，**但只要按 `grep` 结果判断，处理方式完全不同**。

**铁律一：动手前必须先查"谁依赖它"。** 判据一句话 —— **同名的相似 ≠ 重复；被别的技能引用 = 依赖，绝不能删。**

```bash
cd /d/Hermes && grep -rn "<疑似重复的技能名>" skills/ xiaonan-memory/ scripts/ 2>/dev/null | grep -v "skills-archive\|curator_ledger"
```

- **命中活文档**（别的 SKILL.md / DASHBOARD / `related_skills`）→ **是依赖，必须留**，改成模型无关再改引用。
- **只命中 `.curator_ledger.jsonl` / `.usage.json`** → 历史日志，不影响功能，可安全归档旧版。

**实证（差点删错）**：`qwen-image-subject-assets-opc-test` 名字带 Qwen，看着是"Qwen 版的资产技能"，实则是一份**与模型无关的"四视图提示词编译模板"**——`image-prompt`（豆包 Seedream 那套，正在用）第 50 行明写「四视图编译**必须走它的模板**」。删了它，Seedream 的四视图就没人编了。

**铁律二：同名一对多半是"旧版 vs 升级版"，不是双胞胎。** 先开 frontmatter 比 `version:`（本次 0.1.0-rc vs 0.2.0-rc），再 `diff` 看谁多了规则 → **留版本高的那个**，旧的直接进归档柜。

**标准动作（一对约 15 分钟）**

1. **归档旧版**：`mkdir -p D:/Hermes/skills-archive/<类>` → `mv 旧技能 skills-archive/<类>/`（保留可回滚，不删）。
2. **改名去模型前缀**：`mv qwen-image-subject-assets-opc-test subject-assets-opc-test`。⚠️ 目录名带 `-opc-test` 后缀时**先 `find -maxdepth 3 -type d -name "*关键词*"` 拿真实目录名**，别凭印象 `wc`（本次因此空跑一轮）。`mv` 报 `Device or resource busy` 时退回 §4.5 的 `cp -r → sleep 3 → rm -rf`。
3. **改四类内容**（`str.replace` 精确替换，别用正则改结构化文本）：
   - frontmatter `name:`（与目录名一致）
   - `description:`（去掉模型绑定，写清"出图走 XX"）
   - `tags:` 里的模型标签
   - **顶部一行"当前工具 + 换轨日期"**
4. **参数按新模型改**（分辨率/长宽比/步数），**规则段落一个字不动**（锁风全句、四格一致性、EXCLUSIONS 都是模型无关的资产）。
5. **修引用**：把旧名批量换成新名，逐个打印命中数；`image-prompt` 这类"下游依赖方"必改。
6. **验证**：`hermes skills list | grep <新名>` 显示 `enabled`；`find skills -name SKILL.md | wc -l` 对账（改名不改数，归档才减数）。
7. **同步**：`sync_skills.py push` → git commit（commit message 写清"归档旧版 N 个 + 改成模型无关"）。

**改完的长期收益（这才是重点）**：技能变成**模型无关的"编译规则 + 当前工具参数"**，下次换模型**只改参数那一行**，不用再建一个 `xxx-image-*` 新技能、也不会再留下双胞胎。

**⚠️ 别一次推全量。** 先做完 1 对 → 给凡哥看"改了什么/数字怎么变" → 他点头再推下一对。凡哥的规矩是"事一件一件过"。
完整案例（改动前后对照、4 处改动点、grep 证据、体检数字）见 `references/model-migration-skill-refactor-2026-11.md`。

### 4. 修复悬空引用
- ⚠️ **两层都要查（2026-09-24 补）**：① SKILL.md → `references/xxx.md`；② **references 文件之间的相互引用**。第二层最易漏——实战：`opc-style-and-asset-tiering-v0.1.md` 正文引用 `references/opc-style-prompt-vocabulary-v0.1.md`，而该文件只在仓库共享 `references/` 下、没进 skill 目录 → 交付包里就是悬空。查法：
  ```bash
  grep -rh -o "references/[A-Za-z0-9_.\-]*\.md" <skill>/references/*.md | sort -u   # 再逐个 find 校验
  ```
- 官方包扁平化安装的常见问题：SKILL.md 在但 references/ 缺失（seedance 系列是 Emily2040/seedance-2.0 官方包，只拷了 SKILL.md）。
- **正文自足原则**：正文有完整表格/规则时，把 `[ref:xxx]` 替换为"以正文为准"提示，不补不存在的文件。
- 批量替换脚本：解析 frontmatter 拿技能名 → 排除 disabled 列表 → 正则替换缺失 `[ref:xxx]` → 只保留指向真实存在文件的引用。
- 顺带修复：脚本/命令引用缺失时换成真实可用的替代（如 `python scripts/extract_last_frame.py` → `ffmpeg -sseof -0.5 -i <file> -frames:v 1 out.png`）。

### 5. 批量补中文触发描述
- 三种 YAML 格式都要处理：
  - 裸文本 `description: text` → 行尾追加 `（中文触发：XXX）`（全角括号+全角冒号，YAML 安全）
  - 双引号 `description: "text"` → 引号内追加
  - ⚠️ **块标量 `description: |` → 中文放块内容首行，绝不能拼在 `|` 后面**（会 YAML 损坏，computer-use 踩过）
- 写每个技能的中文触发说明要准确（"凡哥说XX时加载我"），不瞎编。

### 6. 验证
- `hermes skills list` 确认 enabled/disabled 数量对账（总数不变）。
- 脚本重新 `yaml.safe_load` 全部 SKILL.md，确认无损坏；统计中文描述覆盖 100%。
- `skill_view` 抽查核心技能加载正常。

## 吃灰体检：技能"利用率"怎么算（2026-10-15 凡哥点名要做）

凡哥原话「**吃灰检查我觉得有必要**」。判据一句话：**技能用得多不多 = 它管的那类事凡哥多常遇到 × 入口（路由表）通不通**。

1. **先看入口，再看频率**：只有挂在 `skill-router` 路由表上的技能才有被主动加载的机会；**没挂路由的技能，利用率跟空壳知识库一样低**（这是最好用的一条判据）。
2. **说得出触发词吗**：一个技能若**说不清"凡哥说什么话时用它"** → 它不该是技能，该并进别的技能或降级成知识库。
3. **实测频次（首选：读 `.usage.json`，2026-11-18 实测）**：`D:\Hermes\skills\.usage.json` 每个技能有 **`last_used_at`** 字段——**这是"用没用过"的最硬证据**，比 mtime 准、比 `session_search` 全。取法：`json.load` 后按 `k.split(":")[-1]` 归一化键名，`datetime.fromisoformat(last_used_at)` 算天数分桶。交叉时必须同时取 `hermes skills list` 的 enabled 集合（**只统计启用中的才有意义**，disabled 和归档不占上下文）。
   ⚠️ **三个坑**：① **幽灵记录** —— 已删除/归档的技能记录还在文件里（本次 `seedance-*` 九个显示"104 天"，`find` 却发现技能根本不存在）→ 必须与现存 `SKILL.md` 目录交叉过滤；② **改名丢记录** —— 技能改名后 usage 键对不上，会被误判成"零使用"（本次 `storyboard-keyframe` / `subject-assets` 刚改名就被报"无记录"）；③ **builtin 常无记录**，不能据此判死活。
4. **次选：`session_search` 查技能名**（要看"当时怎么用的"才用）。⚠️ FTS5 默认 **AND**，词写多了会 0 结果 —— 用宽词/OR（`carnegie OR 卡耐基 OR 人性的弱点`）。本次实证：`carnegie-human-relations` **找到真实使用**（10-14 带团队日报那次先加载它才动笔）；`mishangwo-attraction-system` **只搜到基础设施讨论、无真实使用** → **不是技能不好，是那类事没发生**（判断时要区分"用不上"和"不好用"）。
5. **先看入口，再看频率**（同下条）：没挂 `skill-router` 的技能本来就没机会被加载。
4. **别只看 mtime**：技能被维护过 ≠ 被用过；反过来**低频但必用**的（撩妹 / 月更类）也不能因为"少"就砍。
5. 测量方法论（含 **atime 不可用**的实测证据、可用的 mtime + 使用日志方案）见 `knowledge-base-utilization` —— 技能侧与知识库侧**共用同一套**。

## 技能质量量化体检：为什么"执行不到位"（2026-11-04 凡哥点名"这次要解决根源问题"）

凡哥原话「我们自己的 skill **总会出现执行不到位**的情况」，并要求「贵精不贵多」。**这不是玄学，四个病因都能数出来**（182 个技能全量实测）：

| 病根 | 实测数字 | 后果 |
|---|---|---|
| **① 没有"怎么算做完"** | **59/182（32%）没有验证/检查章节** | AI 干完不知道算不算成 → **"执行不到位"的直接来源** |
| **② 单个体积失控** | 最长 63,761 字（`short-drama-story-engine`）、中位 6,927 字 | 一加载一大坨，重点被淹没，抓不到关键 |
| **③ 描述雷同（两道鱼香肉丝）** | description 归一化前 14 字分组 → **7 组撞车** | 该用没用 / 不该用乱用 / 挑错 |
| **④ 数量失控** | 182 个，**75% 三个月没动**（25% 近 30 天） | 每次开工先扫 182 个"菜名"，慢且费钱 |

体检脚本：`python "D:\Hermes\skills\software-development\skill-library-maintenance\scripts\skill_audit.py"` —— 默认扫 `D:\Hermes\skills`，一次输出上面四张表 + 高危清单（还查无 frontmatter、空壳正文、代码块覆盖）。

**判断"别人给的 skill 是不是水货"的五个问题**（找现成的用）
1. 它解决的是不是我**长期反复在做**的事？ → 否：别装
2. description 写清"什么时候该用我"了吗？ → 否：装了指不准
3. 里面有具体命令/路径/参数吗？ → 否：是空话，装了也执行不了
4. 有"怎么算做完"吗？ → 否：AI 会自我感觉良好地交半成品
5. 近半年更新过、作者还在吗？ → 否：水货概率高
6. **它分了 files 吗** —— 有 `references/`（分步标准）和 `scripts/`（能跑的工具）吗？只有一个大 SKILL.md 的，说明作者也没拆，**装了大概率读不进来**
7. **单个 SKILL.md 多大** —— 用 `git/trees?recursive=1` 一次看全，**超 ~20KB 要警惕**（实测 12–18K 字符就可能被剪枝）

**过四关才装，不到三关直接路过。第 6/7 条是"装得上但用不上"的照妖镜** —— 内容再好，读不进上下文就是白装。

**写自己的技能：六段结构（2026-11-18 凡哥定「按大梁那个博主的方法去写」）**

凡哥原话纠正过我一次：**「我们独有的经验，需要重新写，写怎么去执行，并不是判决书。」**
我此前自夸过"我们写的是判决书，比说明书强"——**那是错的**。判决书 = 写着"我实测过什么/我知道什么"；执行手册 = 写着"下一步干什么"。**只有后者能被照着干出来。**

**SKILL.md 的六段，顺序不能换**（大梁原话："我把实际这个任务：**先做什么后做什么**、**哪个地方必须要让我确认**、**什么状态下才算完成**，全都整理清楚写了下来"）：

1. **name**
2. **description** —— 写死触发词（"凡哥说 XX 时加载"），不写"用于处理 XX 场景"这类空话
3. **⭐ 工作边界（放最前面）** —— 能干什么、**什么情况不该用我**（大梁举例："如果你只是想要压缩视频、提取字幕、或者明确要求用别的动画工具，那就不应该调用这个 skill"）。**放最前，因为 AI 要先判断接不接这活，再谈怎么做。**
4. **执行流程** —— 先做什么、后做什么，动词开头，**给能直接复制的命令**（`python D:/xxx.py 参数`），不写"运行脚本"
5. **⭐ 确认点** —— **"哪个地方必须要让我确认"**。这是最容易被漏、也最致命的一段：**没有确认点 = AI 一路干到底，干完才发现方向错了**。凡哥的真实痛点就在这里。
6. **完成标准** —— "什么状态下才算完成"：看到什么输出算成功、什么算失败、失败回第几步

**四个目录各有各的用处，别混**（大梁原话）：
| 目录 | 放什么 | 判据 |
|---|---|---|
| `references/` | **流程中每一步的标准** | "SKILL.md 规定的是**流程**，references 写的是**流程中每一步的标准**"（例：`command-playbook.md` = 检查那一步用什么命令） |
| `scripts/` | **执行这个任务一定会用到的工具** | 提前写好、跑得起来、不是纸面清单 |
| `assets/` | **素材**（模板/字体/配色/样片） | 大梁："相当于**厨师自己带的调料**……纯文字描述太抽象，AI 做出来会跑偏" |
| 主文件 | **只放流程** | 大梁警告：把每条命令每个标准都塞进 SKILL.md，"这份主说明书就会变得非常的冗长，且难以维护" |

**⚠️ 补一层：判决书挡得住错，教不会对（2026-11-22 凡哥追问「是不是还是那种判决书式的 AI」）**

`write-screenplay` 是这类反面教材的原型：四大死刑、🚫 禁用、❌ 绝对禁止、三大铁律、十八条门禁 —— **骨架整本是禁令清单**。

实测后果（凡哥看完我改的台词，只回一句「**台词很有 AI 味道**」）：照着禁令逐条改，「短句、有停顿、省主语、没有解说、没有复述」**全部命中**，改出来还是假的。因为每句都恰到好处、节奏工整 —— **这本身就是设计感**。真人说话会重复、会卡壳、会自己把自己打断、会说半句咽回去、会跑题、会说废话。

**判据**：一份技能如果通篇是「不许怎样」而没有「先做什么后做什么」，它能挡住低级错误，**却教不会「人是怎么做的」**。禁令从错误倒推，流程从目标正推。

**解药不是再加禁令，是换语料**：想教「人怎么说话」，只能给真人真说的话（实战录音、演试实录、真实求助帖原文），给「不许 AI 腔」的清单没用。以后写这类技能，**先找一份真实样本塞进 `references/`，再谈规则**。

**判定标准只有一条**：**一个什么都不知道的新人，照着它能不能干完。** 写完自己走一遍流程，卡在哪一步就是那一步没写。

**为什么这条比"写详细"重要 —— 体量会从机制上毁掉技能（2026-11-18 实测）**
- 技能正文进上下文，**太长会被压缩剪枝成 `[SKILL_PRUNED]`，剪完就读不到了**。实测阈值：11,985 字符（`hermes-agent-skill-authoring`）、17,759 字符（本技能）**都已被剪过**；一个 105,454 字符的外部技能（`h3-storyboard`）装了也基本读不进来。
- 所以"references 放标准、主文件只放流程"**不是整洁癖，是能不能读进上下文的生死线**。目标：主文件 **3000 字以内**，超了就往 `references/` 搬（**只搬不改，内容一字不动**）。
- 搬家版要标"原文照搬，未改一字"，否则下次分不清哪份是权威。

**补丁次数 = 第七个质量维度（2026-11-18 新增，比体量更能说明"执行不到位"）**
`D:\Hermes\skills\.curator_ledger.jsonl` 记录了每次 patch，按 `skill` 字段累加即得"被打过多少次补丁"。**次数多 = 一直没写对**。本次实测（启用中技能）：
| 补丁次数 | 技能 | 正文 |
|---|---|---|
| **138** | `comfyui-env-ops` | 6.0 万字 |
| **105** | `team-management-ops` | 5.6 万字 |
| **83** | `project-topology-diagrams` | 2.9 万字 |
| 50 | `working-with-fange` | 5.2 万字 |

### 3.8 激进瘦身全流程（2026-11-18 实战：180 文件 / 117 启用 → 146 / 63）

凡哥看完 `.usage.json` 数据后会问「**数量还是很多啊，N 个都有用吗？**」，接着选「**激进**」。这条流程照抄即可。

**三种处置，力度递增，务必分清**
| 动作 | 做法 | 效果 | 恢复 |
|---|---|---|---|
| **禁用** | `config.yaml` 的 `skills.disabled` 加一行 | 文件在，**不加载、不进上下文** | 删掉那行 |
| **归档** | `mv skills/<类>/<名> D:/Hermes/skills-archive/<类>/` | 移出扫描路径 | `scripts/restore_skills.py <名字>` |
| **删除** | 真删 | 不可逆 | 只能靠 git |

**别用"禁用"当"归档"的替代品** —— 禁用虽可逆，但配置文件会越堆越长；真用不上的（模型换代遗留、五个月没动的整组）走归档，**"可能有用但很少用"的才禁用**。

**六步**
1. **先出名单给凡哥看，别直接动手**。按理由分组列（重复 / 从没用过 / 模型换代 / 整组停摆 / 边缘），每类说清"砍什么、留什么、为什么"。
2. **写清单文件**（`cache/cleanup_plan.txt`），脚本读文件执行——**别在代码里手打名字**，手抖一次就误删。
3. **归档脚本要建目录索引**：`glob("**/SKILL.md")` → `{目录名: 路径}`，按名查表 movｅ；**报"未找到"时先 `find -maxdepth 3 -type d -name "*关键词*"` 拿真实目录名**（本次 34 个里 1 个因带 `-opc-test` 后缀没匹配上）。
4. **禁用走 python 脚本改 `config.yaml`**（patch 工具拒改 Hermes 配置）；**改前 `shutil.copy2` 备份**成 `config.yaml.bak-<时间戳>`；正确定位 `skills:` 下的 `disabled:` 段再插 `    - <name>`。
5. **验证三件套**：`hermes skills list | grep -c enabled` 数对账 → **关键技能逐个点名确认还在启用**（本次点名 52 个：写剧本/出图/视频/咨询/管理/招聘/路由/记忆）→ `find skills -name SKILL.md | wc -l` 与归档目录数相加等于原总数。

**⚠️ 别为凑目标数字而砍。** 本次目标"砍到 ~70"，按理由只能凑到 63，**剩下的 7 个砍了就要误伤 8 天内还在用的技能** → 就此停手并如实说明。凡哥要的是"贵精不贵多"，不是"必须砍到某个数"。

**汇报格式**（凡哥要的）：之前/之后的数字对照表 → 砍的分五类清单（带例子）→ **"我验过了，一个都没误伤"+ 点名** → **恢复命令** → 遗留未做清单。

**⚠️ 体检脚本口径**：`skill_audit.py` 默认扫**全部文件**（含 disabled），所以"缺验证 22 个"里混着禁用技能。瘦身后报数前先说明"146 个文件里 63 个启用"，或给脚本加 `--enabled-only`。

### 3.10 判「打架」不只比 description —— 先查同一文件内部的相反指令（2026-11-22 分镜技能去重）

凡哥问「**是不是还有其他的？会不会打架？只留一个就好**」时按这个顺序：

1. **先出清单**：`find_skill.py <关键词>` ＋ 每个技能的 `[启用]/[禁用]/[已归档]` 状态，一行一个。**`references/`、`scripts/` 不算技能，别数进去** —— 本次我把「技能 ＋ 它的施工手册 ＋ 手册里的脚本」报成三个技能，被凡哥当场纠正「**我们不是只找到一个是我们需要的skill吗？**」。
2. **打架的证据要引原文**，两种都会真实发生：
   - 跨技能：description 撞车（`health_check.py` 能报）
   - **同一 SKILL.md 内部自相矛盾（health_check 报不出来）** ← 本次真凶：`skill-router` 第 22 行写「唯一入口 forest-laoli-h3」，第 144 行检查清单仍写「三步链必走（sd-storyboard-engine → h3-storyboard → h3-video-prompt），跳一步就是违规」。第 26 行已写明这条链是《偏心》整版作废的起因，但 144 行没跟着改 → 实际执行照的是 144 行。

3. **动手顺序**：归档重复项 → 改路由（**每一处都改**）→ 扫残留引用 → `health_check.py` → 汇报。`rm -rf` 报 `Device or resource busy` 就用 `cp -r → sleep 3 → rm -rf` 重试。
4. **残留引用分三类**：活路由/流程文档**必改**；**"原文引述"类改成「（原 X 已归档，原文在 …）」保留出处与知识**；历史快照（候选池登记、ORIGIN.md）不改。
5. **"只留一个"＝同类入口留一个**，不是把别的产线的工序节点一起删 —— 依赖没查清就删，等于拿别人的产线换整洁。

### 3.11 动外部技能本体，怎么不被上游更新覆盖（2026-11-23 凡哥要"可恢复、可找回、防覆盖"）

**场景**：从外面装进来的技能（如 `forest-laoli-h3`），实测发现它缺规则，需要**改本体**。凡哥原话：**「动本体 另外记录一下是怎么改动的，方便可以恢复和找到当初改动的内容 也防止更新后改动被覆盖」**。

**第 0 步：先分清这个技能会不会被覆盖**（不是所有技能都危险）

```bash
cd /d/Hermes && find hermes-agent/skills -type d -name "<技能名>"
```

- **有同名目录** → 内置技能，`hermes update` 会覆盖 → 必须做下面四步防护。
- **没同名** → 本地技能，升级不动它 → 改动仍然要记账（为了可恢复），但不用防覆盖。

⚠️ **别用 `created_by: agent` 字段判内置**：它缺失不等于内置——`skill-router`、`working-with-fange` 这些自建技能也没有这个字段，按它判会误判一片。**只认「源码目录里有没有同名」**。

**四步：在技能目录内建一层 `_fange_patches/`（不改上游文件结构）**

1. **建基线**：动手改之前，把**所有可能改到的文件**按原路径镜像复制到 `_fange_patches/baseline_<日期>/`，并记 sha256。
2. **改本体**：直接改 `SKILL.md` / `references/` / `scripts/` 原文件（不搞 shadow 副本——上游升级时要能直接 diff 出差异）。
3. **记变更日志** `_fange_patches/CHANGES_FANGE.md`：每条写四样——**改了哪个文件 / 原文 / 新文 / 为什么改**，末尾附一行恢复命令（`cp -r _fange_patches/baseline_<日期>/* ./`）。
4. **漂移检测** `_fange_patches/check_drift.py`：对比当前文件与基线 sha256，三分类输出——**改动还在**（期望）/ **和基线一样**（被更新冲掉了）/ **基线没有**（新增文件，看还在不在）。

⚠️ **基线必须包含 SKILL.md 本身**（2026-11-23 踩到）：第一次建基线只挸了 references 和脚本，**SKILL.md 没进基线 → 后来改在正文里的几处完全不受漂移检测保护**，被覆盖了也查不出来。**凡是你可能会改的文件全进基线**，别按"这次应该不会改它"筛。

⚠️ **`check_drift.py` 会把「没改过」报成「被覆盖」**（两者都是「和基线一样」）。报告里出现这个提示时，先确认那个文件当初到底改没改，再当事故处理——否则会把正常状态当成灾难。

**为什么用「改本体 + 外层记账」而不是 fork 一份**：fork 立刻与上游分叉，上游修 bug 拿不到、还得长期维护两份。改本体 + 基线 + 日志是「最小代价 + 随时可退 + 升级后一眼看出丢了什么」。

**判据一句话**：跑一次 `check_drift.py`，能不能说清"哪几处改动还在、哪几处被冲掉了"。说不出，就是没做防护。

### 0. 先查合集索引（比逐个搜仓库高效十倍）

找 skill 不要从"逐个搜 GitHub 关键词"开始，**先找那个领域的 awesome-list**。2026-11-18 实战：`UnderleveledBuilder/awesome-short-drama-skills`（★2,529，CC0）收录 **115 个短剧 skill + 16 个开源平台**，按"全流程 / 编剧 / 分镜·视觉资产·视频提示词 / 上游"分类，**并做过三轮盲测排名**（10 个剧本 skill 各写 3 次同一道题、两位 AI 评审盲比），直接告诉你哪几个"三次全赢对照组"——比逐个看 README 靠谱得多。

- 搜法：`web_search("awesome <领域> skills github")`，或 `github.com/topics/<topic>`（如 `claude-code-skills` / `comic-drama` / `ai-video`）。
- **盲测排名可以当选型证据，但要连带它的局限一起说**（该清单自己写明：只测了一个模型、部分条目两位评审结论相反）。
- **同一套流程往往有"通用版"和"专用版"**：本次 `lixiaoxiao9888-create/manju-laoli-skill`（★2,145，通用短剧套装）之外还有 `lixiaoxiao9888-create/forest-laoli-h3`（★84，**只做 MiniMax H3**，带 62K 机检脚本 + 29 个测试用例）。**任务锁定单一模型时，专用版通常比通用版更贴合** —— 但要如实说明它星数低、可能没经大规模验证。
- 找到合集后**先看排名再进仓库**，能省掉大半时间。

### 1. 挑：拿证据，不凭感觉
- 先用 GitHub API 核**真实**数据，列候选对比表再决定：
  `curl -s https://api.github.com/repos/<owner>/<repo>` → `stargazers_count / forks_count / pushed_at / created_at`
- 加分项：**专用**（不是大杂烩仓库的副产品）、**近 3 个月有推送**、作者可信、中文友好（凡哥是中文用户）。
- 交叉验证独立目录的安装量（skills.sh / Skillselion / Awesome Skills 搜索页）。星数与安装量不一致时**如实说明**，别只挑好看的数字。
- ⚠️ 必须向凡哥指出的两点：**单提交仓库突然几千星**（可能是作者名气/刷榜，要标注）；**仓库无 LICENSE**（自用无碍，二次分发要留意）。

### 2. 取：GitHub 文件获取优先级
1. `api.github.com/repos/<owner>/<repo>/contents/<path>` → JSON 的 `content` 字段 base64 解码落盘（**最稳**，单文件可取、无需 clone；列全树用 `git/trees/<branch>?recursive=1`）
2. `raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>`（直取原文）
3. `git clone --depth 1 --filter=blob:none`（整仓，最慢）
某些网络环境下 2/3 失败时 1 通常仍可用 —— 遇到就用 1 写个小脚本递归拉全，**不要因此放弃或改用别的技能**。
⚠️ 未认证 API 有速率限制：**连续拉十几个文件会 `HTTP 403 rate limit exceeded`**（本次装 logo 技能时踩到，12 个文件拉到第 9 个开始 403）→ 每个文件之间 `time.sleep(6)`，或分批取；已取到的先落盘，失败的重试下一批，别整批重来。

### 3. 装：落到技能库

- **frontmatter 的 description 必须补中文触发**（"凡哥说 XX 时加载"），否则中文语境下不触发
- SKILL.md 尾部追加 **「本机环境适配」** 章节：原版假设 → 本机执行方式（python 命令名、缺的依赖、可替代的服务、输出路径规范、实测过的坑）
- 装完跑 `python D:\Hermes\skills\software-development\skill-library-maintenance\scripts\health_check.py` 确认 YAML 完好 / 无悬空引用 / 无重复

### 4. 记：总控台留痕
- `DASHBOARD.md` 技能索引表加一行（类别 / 技能名 / 触发词），并在技能体系段落写清**出处 + 星数 + 本机适配要点**

### 5. 权限提醒（重要）
外部技能装进来默认是**用户所有（`created_by=None`）**，后台 curator **不能**自动 patch 它（真实报错：`Refusing background curator write_file for skill 'X': the skill is not curator-managed`）。
→ 首次实战的坑要么在前台会话里当场回流，要么**明确建议凡哥跑 `hermes curator adopt <name>`** 纳入自动治理，别指望后台自己搞定。

### 6. 验收：必须真跑，**纸面测试不算数**（2026-11-18 凡哥当场质疑「经得起推敲吗」）

装完要判断"哪个好用"时，最容易犯的错是：**读两份 README → 各手写一份样本 → 宣布结论**。本次就这么干了，被一句「**你得出的这个结论经得起推敲吗？**」打回，复盘三条硬伤：

1. **三份样本全是自己手写的** → 比的是"我对规则的理解"，不是"技能本身"。
2. **投入不对等** → A 版认真写满九字段、B 版只写节拍表，拿这个比质量没有意义。
3. **一个镜头都没跑过模型** → 按证据分级（实测 > 官方 > 传闻），这连"官方"都算不上，是纸面推断。

**正确做法（凡哥定的口径）**
- **一个一个来，不混着用**（原话：「不要混着用，要一个一个**严格按照**你找来的 skill 去执行」）。每个 skill 从自己的第 1 步走到最后一步，不借用另一个的规则、不合并输出。
- **同一输入**（同一场戏／同一段剧本），各自产出**它自己的标准产物**（A 出分镜稿、B 出提示词），不强行统一格式。
- **真跑模型**：两边提示词用同画风、同参考图、同 seed 各生成一次，看片子说话。**没跑之前只能说"侧重点不同"，不能说"哪个更好"。**
- 汇报时**先划诚实边界**：哪些是读到的实事（文件大小、章节存在、脚本能跑）、哪些是推断。凡哥认这条，也更信这条。
- 别为了"给他一个结论"而编结论。**"我不知道哪个更好，只测出侧重点不同"是合格答案。**

**前置检查一：先查"格式家族"，别等测完才发现对不上（2026-11-18 差点漏掉）**
能否直接喂目标模型，取决于**它吐的提示词是不是该模型的官方格式**，不是技能好坏。
- **H3 官方 = 六段式**（`subject_definitions` / `summary` / `retention_analysis` / `detailed_description` / `overall_soundscape` / `non_diegetic_music`，全英文仅 `<d>` 内中文）—— 我们自己的 `h3-video-prompt` 明写「官方 Ref2VA，顺序与字段名固定」。
- **一条命令分家族**：`grep -c "subject_definitions\|detailed_description" <技能>/**/*.md`（六段派）vs `grep -c "【画幅风格】\|【时间轴分镜】"`（七段派）。
- 实测：forest / zenstory / h3-storyboard 三个都是六段派（直接可喂）；**`sd-storyboard-engine` 是自创七段式**（要照顾 Seedance 2.5/2.0/H3 三模型，统一用中文方括号），**H3 认不认它至今未验证** → 它只能先当"分镜稿生成器"。
- **分镜技能大多需要"配套下游"**（分镜稿 ≠ 模型提示词）。用**它自己设计的下游**不算"混着用"（那是它的组成部件）；把 A 的分镜规则和 B 的提示词规则搅在一起才算。**对比必须以"端到端方案"为单位。**

**前置检查一·补：真跑的成本已经量出来了（2026-11-19 首次端到端打通）**

可以不再纠结「能不能真跑」，**已经跑通了**：forest 四段 → ComfyUI H3 → 43.37 秒成片（1440×832，带音轨）。
排期用的硬数字：

| 项 | 实测 |
|---|---|
| 一采 960×544 | ≈4.2–4.5 分钟／11 秒段 |
| 二采 1440×832 | ≈8 分钟 |
| 合计 | **≈11–12 分钟／段**；43 秒（4 段）≈ **45 分钟** |

**结论对评测节奏的影响**：真跑一颗 = 十几分钟，所以**横向对比阶段每个技能只跑 1 颗（段 01 那 11 秒）就够了**，
不要一上来跑整集（40 段 × 4 技能 = 160 次 ≈ 30 小时，那是验收阶段的事，不是选型阶段）。
先看「人物有没有按参考图出来、道具对不对、尾巴崩不崩」，这三样 11 秒就能判定，不用等 40 秒。

⚠️ 真跑前必须先过 `comfyui-env-ops` 的 `references/h3-ref2va-production-discipline.md` 四条纪律
（`mode` 写死 `ref2va`、参考图缩到 1024、风格句写首行、一镜一个说话人），
否则会拿到「人物一个都没出现」的片子，白花 40 分钟还误判成「这个技能不行」。

**前置检查二：机检能测什么、不能测什么（别夸大）**
`h3_lint.py`（forest，62K，H1~H36）验三类：① 格式（字段齐全/中文残留/镜行词数）② **H3 已知行为陷阱**（写"镜头切至"→叠化融脸；写"升格/慢动作"→渲染成静止；末镜无定格句→段缝跳帧；H21 台词镜须换嘴切镜）③ 输出质量客观指标（台词填充率/维持句/氛围层）。退出码 0/1/2 可进流水线。
**但机检测不出"H3 遵循度"** —— 脸演不演、画面质感、尾巴崩不崩，只有真跑才知道。**定性：机检是上车前的安检，不是车开得好不好。**
正确流程：**按技能规则产出提示词 → 过机检（免费秒出，筛掉 80% 低级错误）→ 真跑 H3 → 看片子**。强调"机检全绿"时要说清这是"合规"，不是"效果好"。

**前置检查三：目标别漂移 —— 测试任务最容易被"搭前置"吃掉（2026-11-18 凡哥当场拽回）**

### 7. 上游自带 `scripts/tests/` —— 要不要一起装（2026-11-22 判断法）

装外部技能时最容易漏掉的是**上游给机检脚本配的回归用例**。本次 `forest-laoli-h3` 只装了 SKILL.md + 18 本 references + `h3_lint.py`，上游 `scripts/tests/` 下 **29 个用例 + `run_tests.py` + `check_docs.py`（共 94KB）一个没装**。

**它是什么**：`run_tests.py` 里一张 `CASES` 表，每行写明「文件名 / 时长 / **期望 FAIL 数** / **期望 WARN 数** / 用途 / 画幅」，跑一条命令，全部吻合退出 0、任一不符退出 1（作者原话「零放水严格对齐」）。用例命名自带期望：`case05_general_bad.md` 期望 FAIL 11、`case01_ref2va_ok.md` 期望 FAIL 0。

**三个用处，按价值排序**
1. **给机检做体检（最值钱）**：机检一旦静默失效/被放宽，我们会以为稿子没问题。**只要这台秤要交给别人用，就先证明秤是准的。**
2. **正反例教学素材**：每个坑一个正例一个反例（否词、越轴、空间锚、同性别声音混、门窗过早开、画幅 auto/混用、payload 溢出、BOM、全角混排、manifest 截断），给人讲规则不如直接给坏的样例。
3. **判断上游升级**：换版本后跑一遍，就知道新规则是放宽还是收紧。

**边界**：它只测"机检脚本对不对"，**不测内容质量**（拆镜合不合理、台词漏没漏）。别拿它当"稿子一定没问题"的凭证。

**装法**：`git/trees?recursive=1` 里取 `scripts/tests/**` 全量，**按原路径落盘、不改一字**；`run_tests.py` 用 `../h3_lint.py` 相对定位，目录结构不能动。装前先确认本地 `h3_lint.py` 与上游同版（§3.7-bis 的 blob sha 法）。

**装完三件收尾（少一件都算没装干净，2026-11-22 凡哥「不要参杂我们自己的东西进去」）**
1. **复算一遍**：本地文件数 ＝ 上游文件数、逐字节一致 N、**多出 0、缺失 0** —— 本次补齐 `scripts/tests/` + `CHANGELOG.md` 后 = 55/55 全一致。
2. **把之前混进技能目录的自造样本移出到 `D:\Hermes\cache\`**（`mv` 不是 `rm`，留着可追溯），技能目录**只放上游文件**；仓库副本 `shared-skills/` 里那份也要一起删，否则下次 `pull` 又装回来。
3. **跑一次基线并记下来**（本次 `run_tests.py` 29/29、退出码 0）。以后机检改一行、或上游升版本，跑一遍就知道是放宽还是收紧。

## Pitfalls

0. **Self-improvement review 自动创建技能**：Hermes 的 `agent/background_review.py` 会在会话结束后自动从对话中提取经验、生成技能并 patch 现有技能。产生的新技能可能与人工创建的重复（名称不同但内容高度相似）。去重时先查 `desktop.log` 中 `💾 Self-improvement review:` 行确认来源，再把 review 生成的技能合并归档，不要直接删除。
1. **YAML 块标量损坏**是补描述最常见的坑——拼在 `|` 后即坏，必须放块内容首行。
2. **patch 改配置文件/HTML**会被拒或误报——用 python 脚本。
3. **停用 ≠ 删除**；移出目录才是真归档。
4. **curator 归档不看业务价值**——核心技能必须 pin 或调大参数，否则 90 天自动消失。
5. **面向凡哥汇报用大白话**：留什么、清什么、修好什么、保证什么、影响什么；专业术语（相似度/分级）只当内部底稿。
6. 治理后注意系统提示"困难任务后提议保存技能"机制会鼓励技能库重新膨胀——提建议前先问凡哥，不擅自新建。
7. **write_file 写技能目录没有重名保护**——创建技能一律走 `skill_manage(action='create')`（会拒绝重名），只有改已有技能内容才用 write_file/patch。本次用 write_file 直接写技能目录导致与后台 Self-improvement review 自动生成的同功能技能并存。
8. **治理技能的"自动版"可能随时出现**——后台 review 会把当前会话的治理经验自动生成技能；发现与现有维护技能重复时，对比合并进 `skill-library-maintenance`，其余归档，不慌。
9. **别拿「提醒」当「关卡」**（2026-11-18 凡哥当场否掉一个方案后的教训）。给凡哥提方案前先自问一句：**这个办法真的拦得住吗**。脚本、检查清单、流程提醒都只是**提醒**，靠的是执行者的自觉 —— 而重复、拖延、忘事这类问题，恰恰是在「自觉失灵」时才发生。**有效的是结构约束**：收回权限、要求必填证据、提高动作成本，把「必须」变成「做不到就过不去」。凡哥原话：「你要确定，你这个办法真的有用」—— 给方案前先用这句话审一遍自己。
