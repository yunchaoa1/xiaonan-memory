# 技能写作标准 · 大梁六段结构（2026-11-18）

凡哥看完大梁（《保姆级 Skill 通关指南》，16:19，2.5 万赞）的视频后，下了两条命令：
1. 「**我们独有的经验，需要重新写，写怎么去执行，并不是判决书**」
2. 「**是不是和大梁的写 skill 方法一样，不一样要按照大梁那个博主的方法去写**」

要照抄骨架，用 `templates/skill-md-six-part.md`。本文留证据和对照。

---

## 一、大梁的原话（转写摘录，标了时间码）

**SKILL.md 里必须写清三件事（301–311 秒，这段是精髓）：**

> "这里面我写的并不只是'帮我剪一个视频'这么简单，而是我把实际这个任务：**先做什么后做什么**、**哪个地方必须要让我确认**、**什么状态下才算完成**，全都整理清楚写了下来。"

**工作边界放最前（262–273 秒）：**

> "所以我在 skill.md 里面**首先写清楚了**这个 skill 的工作边界，比如说它可以处理口播视频，但如果你只是想要压缩视频、提取视频字幕、或者明确说明确要求使用其他的动画工具，那就不应该调用这个 skill。"

**主文件为什么必须短（312–325 秒）：**

> "这套完整的剪辑流程如果全写完的话，内容会非常多。**如果我把每一条命令、每一种视觉风格、每一个排版标准全都塞进 skill.md 里面，这份主说明书就会变得非常的冗长，且难以维护。**"

**references 是什么（334–347 秒）：**

> "**skill.md 规定的是流程，references 这里面写的就是流程中每一步的标准**……像这个 workflow-playbook，写的是剪视频的工具的工作标准；下一个 command-playbook，写的是检查视频……"

**scripts 是什么（400–419 秒）：**

> "在 scripts 这个文件夹里面就放了两个工具文件……**这些都是提前写好的、AI 执行这个任务的时候一定会用到的工具。**"

**assets 是什么（419–437 秒）：**

> "这里面放的是给 AI 的素材，这个就相当于**厨师自己带的调料**。因为咱们前面所有的内容都是纯文字纯语言的描述，这个对于 AI 来说就太抽象了，它做出来的东西很有可能会跑偏。"

**他也明确说了不是每个技能都要四件套（467–477 秒）：**

> "并不是每一个 Skill 都必须有这样复杂的结构。**有的很简单的 Skill 就是一份 Skill.md 这个文档，它就是一个最小单位的 Skill。**"

→ 所以**判断标准不是"四件套齐不齐"，是"主文件够不够短、流程够不够清楚、该有的标准有没有地方放"**。别拿结构当教条去砍技能。

## 二、"判决书"vs"执行手册"（这次纠正的核心）

### 反例：判决书写法（`comfyui-env-ops` 原第 37 节）

> 崩溃先取完整日志段：`awk '/got prompt/{b=""}{b=b"\n"$0}END{print b}' log | head`——tail 只见栈尾，真实异常在段首（SolAttn 崩因在 `_morton_h3.py`）。

**问题**：这是"我知道什么"。读的人知道有这么回事，但照着它干不出活——什么时候用？看完第一段然后呢？判据是什么？

### 正例：执行手册写法

> **遇到崩溃：**
> 1. 跑这条取完整日志段 → `awk '/got prompt/{b=""}{b=b"\n"$0}END{print b}' <log> | head`
> 2. **只看第一段**（不是最后几行）——真异常在段首
> 3. 判断：报 OOM 但显存空着 → **不是显存问题**，别去调显存
> 4. 把报错原串粘进 GitHub：`"<报错原串>" <组件名>`
> 5. 有 issue → 照做；**没 issue 才动环境**
> 6. 动环境时**一次只改一个变量**

**差别**：前者是结论，后者是动作序列。**同一个知识点，后者能被照着走完。**

### 我犯过的错（别再犯）

我在本轮之前总结过"我们的技能带实测结论，是判决书，比说明书强"——**这话是错的，而且它给"越写越长"提供了正当性**。实测结论有价值，但它的位置是**"踩过的坑"那一节**，不是替代流程。凡哥要的是能执行的流程，附带我们踩过的坑；不是坑的清单。

## 三、体量是生死线，不是整洁问题（PRUNED 机制）

**证据（本轮实测）**：技能正文进上下文后，过长会被压缩剪枝成 `[SKILL_PRUNED: content lost in compression]`，剪完就读不到。

| 技能 | 正文 | 结果 |
|---|---|---|
| `hermes-agent-skill-authoring` | 11,985 字符 | 被剪 |
| `skill-library-maintenance` | 17,759 字符 | 被剪 |
| `h3-storyboard`（外部装） | 105,454 字符 | 基本读不进来 |

**所以"主文件 3000 字以内"不是审美要求**：
- 主文件短 → 每次加载都读得完 → 流程能照做
- 主文件长 → 被剪 → 我只剩个名字，等于没装

**处置长技能的两条路**（凡哥认可的口径）：
1. **只搬不改**：内容一字不动，按章节搬进 `references/`，主文件留索引 + 核心 3-5 条 + 验证标准。每个 references 文件开头注明"从 SKILL.md 拆出，原文未改"。
2. **换掉**：如果是外部技能且内容本身不行，直接归档去找更好的（不要一边修一边留着）。

## 四、找外部技能时的"结构验收"（补充原来那五个问题）

原五个问题（是不是我反复在做 / 触发清不清 / 有没有具体命令 / 有没有验证 / 作者还活着）之外，**加两条结构体检**：

1. **它有没有 `references/` 和 `scripts/`** —— 只有一个大 SKILL.md 的，说明作者也没拆，装了大概率读不进来。
2. **单个 SKILL.md 多大** —— 用 GitHub trees API 一次看全：
   ```bash
   curl -s "https://api.github.com/repos/<o>/<r>/git/trees/main?recursive=1" \
     | python -c "import sys,json;[print(t.get('size',0), t['path']) for t in json.load(sys.stdin)['tree'] if t['path'].endswith('.md')]"
   ```
   **超过 ~20KB 就要警惕**（`sd-storyboard-engine` 37KB 已经偏大）。

### 本轮的两个真实样本（对照）

| | `phileiny/h3-storyboard-skill` | `lixiaoxiao9888-create/manju-laoli-skill` |
|---|---|---|
| 结构 | **只有一个 105KB 的 SKILL.md + 34KB SOURCES.md** | **1 总控 + 10 个子技能**，每个子技能自带 `references/` + `scripts/` |
| 分镜那部分 | 单文件 10.5 万字 | `sd-storyboard-engine/`：SKILL.md 37KB + 7 个 references（含 85KB 投喂格式）+ `check_p45.py` |
| 内容质量 | 极高（每条规则标了验证状态，有 PSNR 对照实验） | 极高（12 条套装契约、机检 C1~C33、台词承接契约） |
| 能不能用 | **装得上、读不全** | **能读、能跑脚本** |
| 结论 | 留作对照 / 需要"只搬不改"才能用 | **符合大梁结构，可原样用** |

**教训**：**内容好 ≠ 能用**。挑外部技能时先看它有没有按"流程 + 分步标准"分文件，再看内容。

## 五、外部技能怎么测"好不好用"（本轮做的三方对比，可复用）

凡哥要求「把装好的全测一遍，选出最好用的」。做法：

1. **固定考题**：同一段真实剧本（本轮用《末位》第 002 集场 03，12 句台词、一个场景、情绪有谷底和峰值）。
2. **各自按自己的规则真拆一遍**（不是读一读评价，是产出成品）。
3. **固定维度打分**（本轮六维）：一镜塞多少节拍 / 台词是否全承接 / 时长与帧数处理 / 有没有省生成的复用判断 / 机位规则是否适配画风 / 能不能直接投喂目标模型。
4. **找反面教材**：在自己的旧产出里找一条最能说明问题的（本轮是 `镜 19｜15 秒` 塞 6 句台词 + 5 个动作，且顶满 15 秒无尾巴余量）。

**本轮结论**（写在这里当案例，具体结论凡哥还没拍板）：两个外部技能各强一半——`sd-storyboard-engine` 管结构/机位/台词契约/机检，`h3-storyboard` 管 H3 的物理极限（一镜 2-3 个节拍上限、帧数 17n+5 格点、尾巴留 1.3-1.5 秒、素材复用省生成）。**"选一个"未必可行时，如实说"要两个配合"，并给出流水线顺序** —— 别为了迎合"选一个"而藏掉短板。
