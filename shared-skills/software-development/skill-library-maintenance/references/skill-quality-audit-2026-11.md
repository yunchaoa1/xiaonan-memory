# 技能质量体检 & 标准对照（2026-11-04）

凡哥丢来抖音「保姆级 Skill 通关指南」（大梁，2.5 万赞 / 2.2 万收藏，16 分 19 秒），
要求：①学他的理解 ②对比我们自己的做法 ③定"找/验 skill"的标准 ④清理现有库。
原话：「**我们自己的 skill 总会出现执行不到位的情况，我想这次我们可以解决这个根源问题了**」
「有用的留，没有用的和重复的都删掉，要做到**贵精不贵多**」

---

## 一、大梁（马导）的观点 —— 8 章提纲

| 章节 | 观点 |
|---|---|
| 引言 / 作用 | 提高 AI 任务完成的**质量和稳定性**，适用于"不擅长"或"重复性"工作 |
| 什么是 Skill | 「给 AI 做事的**流程和标准**，以及提供任务所需**工具和素材**」；本质是电脑里的一个**文件夹** |
| 组成部分 | **SKILL.md**（主文件，不可缺）+ **references** + **scripts** + **assets**；最简技能可以只有一份 SKILL.md |
| 主文件结构 | 顶部 `name` + `description`；**description 决定 AI 用不用你** —— 写模糊＝不知道何时调用，写太宽＝不该用时乱触发 |
| **副作用①** | AI 每次开工**先读所有技能的 name + description**；他打比方：菜谱 5 道菜好找，**500 道菜光看目录就累死**（费时间、费 token） |
| **副作用②** | 功能相近的技能描述也相近 → AI **挑不出该用哪个**；比喻：菜单上两道鱼香肉丝（"招牌"和"B点"）却没写区别 |
| 判断标准 | ① **长期反复在做** ② **流程和标准相对固定** ③ 提稳定性 / 解决常见问题 |
| 获取与使用 | 内置功能区、GitHub；用前要弄清**功能 + 触发条件**，并测试 |
| 总结金句 | 「提示词、skill、agent、MCP 这些**其实只是 AI 的使用方式**；**只有你自己知道这件事该怎么做、该做成什么样，你才能判断 AI 做得对不对**」 |

**他的结论**：「skill 并不是装得越多越好，**贵精而不贵多**。」

---

## 二、我们的做法 vs 他 —— 三条根本不同

1. **他是"买菜谱的"，我们是"写菜谱的"**
   他整条视频重心是"怎么找现成的来装"（GitHub / 市场）；
   我们 182 个几乎全是自己写的，每个都是踩过坑才落下的（如"抖音长视频必须单独抓音轨"）。

2. **他教"说明书"，我们写"判决书"**
   他的 SKILL.md 以流程为主；我们的技能里大量是**结论**，例如：
   「Obscura 快（0.9 秒），但抖音过不了验证码中间页 —— 替代 Lightpanda，替代不了 Camoufox。」
   → 这不是步骤，是判决，让未来的自己不用再试一遍。

3. **他靠 description 让 AI 自己挑，我们多一层 `skill-router` 总调度**
   好处：不会漏。坏处：条目越加越长，维护成本高。

**认知层面完全一致（定义 / 组成 / 判断标准都对得上）；做法层面我们更狠；管理层面他比我们清醒。**

## 四、给凡哥的施工顺序（他已认可"先定标准再动刀"）

1. **B 写标准**（治执行不到位，最直接）
2. **C 清理**（用 B 的尺子：删 / 并 / 改）
3. **A 找现成的**（最不急 —— 实测里大多数新项目用三个筛问题就过滤了）

**两条执行纪律**：
- 清理**先给第一批改动样本**让凡哥确认，再全量推；不一次性动 182 个。
- **不确定的一律归档不删**（`skills_archive` / `xiaonan-memory/skills-archive`），随时能翻回来。

## 五、顺带产出的方法论（凡哥丢新项目时的三个筛问题）

1. **它解决谁的问题？** 解决开发者的 → 路过；解决使用者的 → 可看
2. **我有没有那个条件？** 要 80G 显存 / 要写代码 / 要买服务器 → 路过
3. **不做会怎样？** 没影响 → 路过；会错过赚钱机会 → 认真看

本次用它筛了 6 个项目，只有 2 个留下（Opus 5.5 代码动画、HyperFlow H3 Flash），
其余（OpenGCUA / Harness² / Agent Lightning / 街景站）全部"路过"。
**结论沉淀在 `tech-radar` 技能里，不重复研究。**
