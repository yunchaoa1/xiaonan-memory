# AV 生成故障排查（Evidence-First Troubleshooting）

## When to Use

AI 生成视频/音频出现异常时（杂音、低频嗡、爆音、画面重复/分屏感、质量倒退），需要**定位根因**而不是试错重跑。也用于验证"某个环境因素是否问题根源"（如模型版本、框架版本、参数、提示词）。

## 铁律（凡哥 2026-09-03 明确纠正）

1. **先查官方 issue 和社区同病案例，再动手**——"别瞎猜瞎试，去官方找问题所在，精准处理"。GitHub issues（官方 repo + 插件 repo）和社区实测帖子往往已有根因+解决方案。
2. **对比排除法**：一次只变一个变量（版本/工作流/提示词/参数），设计对照实验，不盲目重跑试错。
3. **证据优先**：诊断结论要有客观数据（频谱、日志、时间戳、文件对比），不靠"听感+推测"下结论。
4. **别拿推测当结论**：因果链没做对照验证前，明确区分"实锤的事实"和"待验证的推测"。
5. **测试阶段只跑一采/最低成本路径**：能判定的最小产出（如一采带音频的 seg mp4）就够，不跑完整流程。
6. **工作流类故障：先去该工作流的 UP 主官方信息里找方案，再动手**（凡哥 2026-09-18 纠正：『你去看这个 up 主的官方信息，从那里找方案修，**不要自己瞎试**』）。
   - 「官方信息」三处优先级：① **UP 的视频教程**（讲工作原理与参数取舍）② **工作流 json 里的 MarkdownNote / 作者 B 站主页 / 网盘说明** ③ **插件源码**（节点参数定义、tooltip）。
   - 本次反面教材：在未看教程时自行推断出「cudaMallocAsync 分配器高压崩 → 加 `--disable-cuda-malloc`」，写进 skill 后被凡哥当场打回——真根因是 UP 早就讲过的「参考图不缩放会暴显存」。
   - **自创方案只能标"待验证"**，不得当结论写进 skill 或交付；**工作流身份也别凭印象**——从 json 的 MarkdownNote 读作者（本次实录：一直记成"小黄瓜"，实际是 **Astral星芒**）。

7. **★ 先在宿主系统之外做「最小隔离复现」，再在系统内逐层猜**（2026-10-08 纠正；同一天因违反此条被凡哥质问『**你是不是找不到原因在瞎试？去找靠谱的方案来啊**』）。凡哥容忍「一次只变一个变量」，但**不容忍在错误的那一层反复换变量**。反面教材：一个 `Tensor input must be on CUDA` 报错，在 ComfyUI 里连试三轮（改插件设备检查 → 加启动开关 → 翻插件版本）全落空，最后**一条 10 秒的隔离测试**（把报错那一步拎到纯 python 进程里跑、零 ComfyUI 参与）直接锤死真因 = 预编译 CUDA 扩展与 PyTorch 大版本 ABI 不匹配，**与工作流 / ComfyUI 全无关系**。
   - 判据：**炸 ⇒ 是组件本身的问题，宿主里怎么调都没用；不炸 ⇒ 才轮到宿主当嫌疑。**
   - 越「寄生」的组件越要先隔离（pip 装的 C++/CUDA 加速库、monkey-patch 型插件、共享库依赖）——它们在宿主里的报错位置和真因往往隔着好几层。
   - 配套两个通用判据：① **`print` 放进条件里**，一个字都不打印 = 假设是错的；② **报错栈行号位移** = 补丁确实落地（区分「没生效」与「生效了但没用」）。
   - 与第 1 条（先查官方 issue）是一件事的两面：**先查社区同病案例 → 再做隔离测试 → 最后才在宿主里调参**。
   - **交代口径**：凡哥问「**你实话说是不是解决不了？**」时，正解是「直说 + 给已确认的事实 + 给一个今天就能用的保底」，不是继续给下一个待试项。本次保底 = `Ctrl+B` 旁路那个加速节点用原生 attention 先出片（代价=显存峰值升高、偏离标准版，属他决策事项）。**别把「还在试」包装成「快好了」。**

## 音频异常诊断：频谱法

**嗡声/杂音/爆音的判定不要只靠耳朵**，用频谱数据：

1. `ffmpeg -i <视频> -vn -acodec pcm_s16le out.wav` 提取音频
2. numpy FFT 分频段能量：<200Hz / 200-500Hz / 0.5-6kHz（人声区）/ >6kHz，加每 5 秒窗口主峰
3. 判据：
   - **嗡声**：无台词段也有 60%+ 能量在 <500Hz，人声区几乎为 0
   - **正常**：无台词段能量在中频（抽泣/水声/摩擦声）；台词段低频成分是**人声基频**（女声 165-255Hz、男声 85-180Hz）——低频占比高 ≠ 杂音，勿误判

可复用脚本：`scripts/audio_spectrum_check.py`

**注意**：先核对用户已有的实测事实（如"单段正常、多段杂音"）再归因——问题可能只在特定路径（长帧/多段/特定模式），不要轻易归到"模型能力"。

## 版本因素对照实验法

当怀疑"某框架/插件版本是根因"时，用**双版本独立部署**做对照（唯一变量=版本）：

1. 下载目标版本的独立安装（便携版/独立 venv），**不动现有生产环境**
2. 共享大模型文件（挂载/软链，不重下）
3. 复制必要插件 + 装同版本依赖（关键依赖版本照抄现有环境）
4. 同工作流、同 seed、同提示词各跑一次，对比输出
5. 判定后决定生产路径（切换版本 / 等官方修复合并 / 打官方补丁）

**镜像/托管环境警示（2026-09-09 实测教训）**：整体切 ComfyUI 版本前先查插件配对——预装镜像的 custom_nodes 常依赖特定小版本新增的 API（案例：LTXVideo 在 0.30.0 上 `ImportError: cannot import name 'interleaved_freqs_cis' from 'comfy.ldm.lightricks.model'`），降级后部分插件 import 失败、采样期直接原生崩溃（日志特征：尾部整段 `Extension modules: ...` dump + `Fatal Python error: Aborted`，且服务"端口起来了"但一 Queue 就死）。动手前用 `git diff <旧tag> <新tag> -- comfy/ comfy_extras/` 看后端差异：**小版本若只 bump 前端包（后端零差异），降级毫无意义**。

案例：H3 音频低频嗡的**干净版本 = 0.30.0 与 0.30.1**（两者后端 comfy/、comfy_extras/ 代码零差异，git diff 实锤；0.30.1 只是 bump 前端包）；嗡声在 0.30.2/0.31+；**官方最新 0.33.x 仍未修复**（#15799：音频恒定 DC/静音，试遍变量全失败）。**已验证的修复路线**：①Windows/本地 = 便携版 0.30.0 并存；②Linux 托管定制镜像整体降级 = 已实测失败（镜像插件配 0.30.1，切 0.30.0 后插件 import 失败、采样期原生崩溃 Fatal Abort）；③**云托管（智算云扉 waas）= 从基础 pytorch 镜像干净重建 v0.30.0+本地配套插件组合，2026-09-09 凡哥亲验 8s 一采无杂音 ✓**（完整命令链+平台机制+坑，见 `references/waas-cloud-h3-rebuild-case-2026-09.md`）。本地/旧镜像细节见 `references/h3-audio-noise-case-2026-09.md`。

**云平台机制先查官方文档（凡哥 2026-09-09 纠正："别瞎猜"）**：托管环境的镜像语义、自启机制、数据盘持久性、模板覆盖行为都**只有平台官方文档（如 docs.aigate.cc）+ 实测说了算**，不要拿通用 ComfyUI/Linux 经验脑补（实测教训：改 `/etc/waas-script/process-compose.yml` 加自启进程会被平台 entrypoint 开机模板还原）。平台文件系统分三类：持久数据盘（环境放这）、系统盘可写层（重启保留但 entrypoint 可能模板覆盖）、镜像层（重启还原）。

## 高清/2K 放大路线（2026-09-09 云端 32GB 实测教训）

**Director（AIMixer）refine upscale 到 2MP(1920×1088) 在 32GB VRAM = 物理 OOM**，逐层排查结论：
- h3_latent upscaler 官方 README 明说 **"saves time, not VRAM"**——放大后精修仍在目标分辨率跑，峰值 ≈ 直接生成高分辨率
- 换 pruned/nvfp4 小模型（staged 32.4→19.9GB、TE 25.8→14.9GB）后**仍 OOM** → 元凶是 2K latent 采样激活峰值，不是模型大小
- sageattention：**PyPI/tuna 最高只有 1.0.6**（无 2.x）；KJNodes sage 节点要 2.x 的 `sageattention.core`（1.0.6 无此模块 → "not new enough / could not determine CUDA architecture"）
- SolAttn(tau 1.2) 替代 sage 在 **3 步 refine 无效**（稀疏窗口 start0.2~end0.9 在 3 步中几乎不生效）
- turbo LoRA(4step v1.1_768p) + 2MP 大放大 = 细节修不动 → 成片比一采糊
- OOM 日志铁证行：`[WARNING] Segment 1 refine failed (Allocation on device); keeping last successful pass.`（= 静默回退一采放大结果，无精修）——凡哥看到的"直接出片、比一采糊"即此

**正解 = 绕开 Director，用官方原生模板**（ComfyUI 0.30.0 自带）：
- `MiniMaxH3ReferenceToVideo`（前端 Library→Video→"MiniMax H3：参考生视频"），参考图 ref_image_0..8 + 音频/视频参考，提示词=自然语言 + `<Picture N>`（非 Director 六段）
- 2K = ResolutionSelector megapixels 2.0 **直接一采生成**（无二采概念；流程=0.4 低清验收 → 同 seed 拉 2.0 重跑）
- 模型最低档：ref2va_pruned_int8_convrot + qwen3vl_nvfp4_awq（官方 ~24GB 级，宣称 dynamic offload 下 3060 可跑 2K）
- **官方原生模板音频干净（凡哥实测）**——⚠️ 归因纪律（凡哥纠正）：音频干净根因是 **ComfyUI 0.30.0 版本**（Director 在此版本同样干净），**不是"绕开 Director"本身**。不得把版本因素归因成组件因素。

## 官方原生模板加速与生态更新（2026-09-09 二期查证/实测）

**加速点**：官方 r2v 模板 model 链 = UNETLoader →(可插 TESpeedMiniMaxH3 → SolAttnPatch)→ BasicScheduler.model + BasicGuider.model（UNET 输出 fan-out 两节点）。TE ≈45%（本地实测）；SolAttn 稀疏窗口在 **20 步才有效**（3 步 refine 无效见上）；base 保持 20 步。

**Turbo LoRA 生态更新（旧"Turbo 仅 FL2VA"作废）**：社区 larryvrh Turbo v4 支持 T2V·I2V·FL2V·**Ref2V Mixed**；`minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16.safetensors` 已进官方 HF 打包（datasets 有）。ref2v turbo 用法：steps 20→**8**（作者推荐 6-8 步，不是 4），sampler 保持 res_multistep/euler + simple。诚实边界：ref2v turbo v0.1=社区预览，**参考图锁角色保真最不稳**；turbo=试镜/预览工具，终稿回 base 20 步；turbo LoRA 必须与 FL2VA/Ref2VA 家族匹配，不混用。4 步 vs 20 步 ≈采样 3.4×（端到端少些，编码/解码/加载固定开销不缩）。

**官方模板 json 格式坑**：官方下载的 API 格式 json（~7KB，class_type 图）**拖入前端不渲染**（节点为 0）；要 UI 格式（nodes/links 数组）——前端 Library 打开的是 UI 格式；本地模板包路径 `.../site-packages/comfyui_workflow_templates_json/templates/video_minimax_h3_r2v.json`。在 UI json 手工插加速节点遵守 json 铁律（links + 两端端口同步）；LoraLoaderModelOnly 插 UNET 与 sampler 之间。

**/datasets 平台公模库部署模式**：只读公模库**软链到共享盘即用**（免下载免复制）：`ln -s /datasets/ComfyUI/models/<子目录>/<文件> /home/waas/ComfyUI/models/<子目录>/` + 重启 ComfyUI 扫模型。本次软链 3 文件：ref2va_pruned_int8_convrot、qwen3vl_nvfp4_awq、ref2v_turbo_4step_v0.1。

**15s(362帧=17n+5) 2K 硬件档位（官方数据+诚实边界）**：官方无"2K×15s"专项数字；pruned INT8+NVFP4 整档 ≈24GB VRAM（官方称 12GB 靠 dynamic offload 可能跑）；社区实测 12GB 卡 FL2VA 2K 124帧 4步 turbo ≈8min（帧数是显存主因子）；ref2va pruned + 2K×15s 在 32GB = **无公开先例需实测**，建议测序 2K×8s → 1MP×15s → 2K×15s+turbo8。

**手工搭 ComfyUI json 工作流铁律**（本次踩坑）：只往 `links` 数组加线**不会画线**——必须同步更新节点端口的引用：from 节点 `outputs[i].links`（数组）append link id、to 节点 `inputs[i].link` 设 id；且节点定义若缺该口（json 只存用到的可选口），须整节点换成含完整端口的定义（如 Director 需带 refine 口/out6 的版本）。校验=遍历 links 反查两端端口引用。

## 高清成片三期结论（2026-09-09）：32GB 上 2K 的正确姿势

**放弃两条路**：① Director 2K 二采 = 32GB OOM（见上）；② 官方模板 2K 直出 = 分辨率悬崖（5090 实测 1080p=3.5h；wan2-7 实测峰值显存 ~31.8GB 全打满，pruned 不省峰值显存）。**正路 = ≤0.7MP 低清直出 + 外部放大**。社区 5090 权威数据、RTX VSR 实测与补丁、LTX2.5 跨模型放大（UP 实测主推，IC-LoRA 带参考图保脸）详见 `references/h3-2k-upscale-vsr-ltx25-2026-09.md`。

**快速要点**：
- 8s 档时间（5090）：0.3MP≈2min / 0.5MP 4m17s / **0.7MP 7m26s（最值档）** / 1.0MP 13m49s；15s(362帧) 安全档 ≈0.5MP（帧数×1.9 等效显存）。
- **RTX VSR**（Nvidia_RTX_Nodes_ComfyUI + pip nvidia-vfx）：2× 放大 11.2s/362帧；**quality 必须 HIGHBITRATE_HIGH**（原版下拉只有 LOW/MED/HIGH/ULTRA=删扩散纹理→比原糊，需一行补丁加档，见 reference）；纯超分无角色参考 → 救不回小脸/远景脸（凡哥实测质疑成立）。
- **LTX2.5 放大**（凡哥选定路线）：Spatial Upscaler 2× + IC-LoRA ingredients(0.9) 多图参考 + 音频引导 + 3步 denoise 0.25 → 去模糊保脸；5090 8s 2× 放大 3分14s、10s→1080p 3分43s 显存 25.9GB；模型 6 文件全在官方 HF 仓库（Lightricks/LTX-2.5 + Lightricks/LTX-2.3-22b-IC-LoRA-Ingredients），云上下载走 `HF_ENDPOINT=https://hf-mirror.com`。
- **纯超分/跨模型放大的共同边界（凡哥 2026-09-09 纠正）**：放大救不回"源就没拍清"的脸（无中生有=脑补=变脸）；脸要保真靠生成时脸够大（写 close-up）+ 参考图注入，不是靠放大环节。
- **★ 二采/放大前必须先处理参考图尺寸（2026-09-18 实证，UP Astral星芒 官方方案）**：`MiniMaxH3ReferenceSplitter.short_edge_max` 的 **`0` = 不缩放**（插件源码 tooltip 原文 `Short edge max pixels; 0 = no scaling.`）→ 大参考图（本例 1440×2560 / 3.7MP）**原样参与二采** → **32GB 也暴显存**，症状是 `cuMemFreeAsync` 报 `CUDA_ERROR_INVALID_VALUE` + `Fatal Python error: Aborted`（崩在 tensor 析构/释放路径，**别误判成"分配器 bug 要加启动参数"**）。
  UP 原话：「你传入的图片如果是 2K 的，参考的图片就是 2K 的，这个时候就很容易暴显存」。
  **正解**：把 `short_edge_max` 设成 **544（≈一采短边，最省）/ 816 / 1088**（`align_to` 保持 16），或喂之前先缩放参考图文件。完整因果链、被否定的自创方案、工作流作者归因法见 `references/h3-refimage-scaling-vram-crash-2026-09.md`。

## ComfyUI 内核升级 → 插件崩溃排查（2026-09-09 云 0.30→0.35 实测）

**凡哥暴怒纠正（铁律级）**：进程崩溃时**禁止在没看完整日志前断言原因**（本次连错：先猜显存边界→被小参数也崩证伪；再猜 cu128→升 cu130 仍崩）。崩溃取证与版本对应全链见 `references/comfyui-upgrade-crash-2026-09.md`，速记：

- **崩溃特征**：exit 134（SIGABRT）+ `Fatal Python error: Aborted` + 栈底 Extension modules dump = C/CUDA 层硬崩（插件与内核不兼容），不是软 OOM（软 OOM 有 Python 报错）
- **取证命令**：`awk '/got prompt/{buf=""} {buf=buf"\n"$0} END{print buf}' comfyui.log | head -60`——tail 会截掉栈顶真实异常（指向具体插件/代码行）
- **对照判据**：参数缩到已知稳档还崩 = 环境/插件问题，不是资源边界
- **0.35 内核实测**：第三方 H3 加速插件（SolAttn_triton/TE-Speed）按 0.30 内核 `minimax/model.py` 结构 monkey-patch，0.35 重构后 TE 静默失效（日志 no block_loop hooks）、**SolAttn 崩**（_forward 设 model 属性 → Fatal Abort）；triton 3.4/3.8 同点崩 = 与 triton 无关
- **官方加速正解**：0.35 内置 `--use-sage-attention`（免插件，H3 ~2×）；工作流带 SolAttnPatch 节点必须换官方原生模板
- **LTX-2.5 需 ComfyUI ≥0.32.0**（官方 Day-0）；VAE size mismatch（conv_out [48,256] vs [3,512,3,3]）= 内核太老非文件错
- **torch cu130 升级坑**：pip 不带 `-U` 不升级已装 torch → 部分升级版本错配 libcudart 崩；三件套必须 `-U` 同源（torch 2.14/torchvision 0.29/torchaudio 2.11 号体系不同，锁版先 `pip index versions`）

## 画面异常（重复人物/分屏感）排查线索

- 参考图是"同一人多视图宫格"（四格/四宫格）时，模型可能学出"画面里多个一样的人做同样的事"
- 候选解法：参考图拆单张喂 / 提示词明写"每人画面内只出现一次"
- **未验证假设，验证前不能当规则写进提示词 skill**

## 画面异常（写了但脸没动 / 片尾崩成噪点）—— 2026-11-18 外部实测

这两类是**模型机制**型异常，不是环境/插件/版本问题。**先查镜头结构，别去翻 ComfyUI 版本**（对照本文上半部分的版本排查路径，别走错门）。

### 症状 A：表情写了一大堆，画面上脸几乎不动（冻帧感）

**根因**：一颗镜头里塞了太多"表情节拍"，H3 会往**平均运动**收敛，把它们全部抹平 —— **不报错、不警告**，就是给你一张面瘫脸。

**证据**（来源：外部 skill `phileiny/h3-storyboard-skill` 的对照实验，同 seed／同参考／同面部指令，每次只改一个变量；其 `SOURCES.md` 标注了哪些有对照、哪些仍是推断 —— **我们未自行复现**）：

| 版本 | 结构 | 情绪峰值 PSNR | 结果 |
|---|---|---|---|
| A | 一颗 7 秒特写，塞 **9 个**表情节拍 | 37–42 dB | **脸完全没动**（42 dB = 冻帧） |
| B | 拆成三颗 2–3 秒，各 **1 个**主节拍 | 22–23 dB | 表情全部到位 |
| C | 同 B + 加 `<d>` 对白标记 | 19 dB | 幅度更大 |

**诊断法（不用做对照实验就能判断）**：数这颗镜头里表情变化几次（睁眼／扬眉／咬唇／张嘴各算一次）。**>3 次 → 就是它**。

**修法**（顺序别反）：
1. **拆镜头**（主因，贡献绝大部分效果）：拆成 2–3 秒一颗、每颗一个主节拍；
2. 再把台词写进 `<d>`（加成项，不是机制）；
3. 别指望"写细一点"能救 —— 塞太多时模型根本不执行。

**注意**：这跟"每镜最多 4 个可演状态"是**两个维度** ——
- 4 个状态上限管「讲得清吗」（叙事层）
- 2–3 个表情节拍上限管「演得出来吗」（渲染层）
**两个都要过。**

### 症状 B：片尾 1.2–1.7 秒崩解成噪讯色块

**根因**（两条，常叠加）：
1. **没留尾巴余量** —— 时长按"目标秒数"填满，实际生成会把尾巴落在崩解区；
2. **Duration 填了整数秒** —— 会吸附到**多出来**的帧，**那段没有提示词 → 尾巴崩**。

**修法**：
- **每颗留 1.3–1.5 秒余量**，不要把 15 秒顶满写 15 秒的内容；
- **帧数取 17n+5 格点**（24fps）：124=5.17s｜158=6.58s｜192=8.00s｜209=8.71s｜243=10.13s｜362=15.08s；
- **Duration 填「略低于目标秒数的一位小数」**（要 6.6 填 6.5），让它吸附到目标格点；
- **每颗拍完抽末段帧检查**（不是只看开头）—— 暗部场景肉眼快转不易察觉；
- ⚠️ **别把"跑过最长的一颗"写成"模型上限"**：笔记写"实跑到 N"，不写"上限 N"（362 帧／15.08 秒实测一次成功过，而 209 帧曾被误当天花板）。

**这条最容易误诊**：因为它是"看起来出片成功、只是结尾糊"，很容易被归到编码/后处理/放大环节去查 —— **先看时长与帧数有没有顶满**。

### 症状 B-2：人/物跟设定不符（性别反了、多一个人、道具不对）——「图赢过文字」，先开原图再怪模型（2026-11-22 凡哥当场戳破）

**事故经过**：剪影片设定「一男一女隔桌对谈」。出片是**两个男人**。我判定「H3 把女性画成男性、远景扛不住身份」，写进汇报让凡哥看。

凡哥一句话戳破：**「性别没改过来是你给喂的图就是两个男人吧？」**

回去把原图放大看——**就是两个男的**。生图阶段的提示词只写了「两个人隔桌对坐」，没写性别，生图模型默认画了两个人；H3 忠实照图走，一点错没有。

**根因链（三步都是我的错，模型一步没错）**：

| 步 | 发生了什么 |
|---|---|
| ① | 生图提示词没写性别 → **图里就是两个男人** |
| ② | 写视频提示词时按脑补的剧情设定写「一男一女」→ 文字和图打架 |
| ③ | 出片按图走 → 我拿文字去怪模型 |

**判据（以后先过这关，再下任何结论）**：

- 出图的人／道具／场景跟预期不符 → **第一步打开原图看**，不要先查提示词、不要先怪模型、不要先归因成「模型能力上限」
- **图里没有的东西，文字写一百遍也长不出来；图里有的东西，文字否不掉**
- **性别、人数、年龄感、服装、道具** —— 这类靠轮廓判定的属性**全靠参考图定**，提示词只是复述
- 图和设定不一致 → **先改图**（重生／换图），不是加词硬掰。加词跑出来的仍是图里那个人

**连带的口径纪律**：跟凡哥汇报「模型做不到 X」之前，先自查一遍素材。**把「我喂错了图」说成「模型不行」，是最伤信任的一类误判**——他会据此去做错的技术选型。

⚠️ **诚实边界**：把参考图改对（生图提示词写明性别与体型）之后，H3 在**远景／纯剪影**这个尺度上能不能保住性别，**尚未验证**。已知的机制事实是：远景画不清身份（原 `h3-storyboard` 的原话「远景只有一个正确用法：做空间，不做身份」；该技能已于 2026-11-22 归档，原文在 `D:\Hermes\skills-archive\creative\h3-storyboard`）。所以「图对了就一定能保住」这句话现在**不能讲**，得先跑一颗看过再说。

### 症状 C：动作写了，但画面上没做 / 做成了别的动作（2026-11-19 真机实证）

**四类根因，按命中率排序。先数词，再查术语，再看接触方式，最后查 Subject 引用。**

#### C-1 动作没做出来 → 先查「是不是只写了个动词」，不是先查词数（2026-11-21 修正）

⚠️ **旧口径「单镜 ≤70 词 / >100 丢指令」已作废。** 那是把「写得含糊」误诊成「写得太长」。

**对照实验**（同一场戏、同 5.17 秒／124 帧、同三张参考图、同机位，唯一变量＝写法）：

| 版本 | 词数 | 实测结果 |
|---|---|---|
| 短版（动词式） | **64** | **只画出「手搭在肩上」**，她笔直站着还带笑，像领导拍肩 |
| 长版（物理链式） | **516** | **真推了**：上身后仰越过髋线、眼睛紧闭眉头皱、双臂张开找平衡、退开半步 |

**同一颗镜、同一时长，516 词做的动作比 64 词多。** 另有 14.3 秒长镜写 760-840 词、八拍动作全做完的实测。

**真正决定成败的是：动作有没有写成物理链。**

| 写法 | H3 的反应 |
|---|---|
| `pushing into her shoulder`（4 词） | 手放在肩上，就到此为止 |
| 掌心沿可见路径落到锁骨下方 + 压得她上身越过髋线 + 布料在掌心周围堆起 | 真的推了 |

**动作物理链五段，缺一段就退化成摆姿势**：
1. 出发（哪个部位动：掌心／拳面／膝盖）
2. 路径（沿一条看得见的线走）
3. 落点（精确到身体部位）
4. 接触后果（受力方的几何变化：后仰、越过髋线、头仰起、布料起皱）
5. 重心与恢复（退半步、脚跟撞椅腿、手臂张开稳重心）

**判定口诀**：数一数这一句里有几个「物理事实」。只有动词 → 一个都没有 → 必废。**H3 不认动词，只认物理。**

#### C-2 影视行业术语 H3 一个都不执行

这些在分镜圈是标准语言，写进去等于白写：

| 写了 | 实际反应 |
|---|---|
| 「画面顿住两帧」/ 顿帧 / 冲击帧 | **完全无效果**；"两帧"可能被当成画面里的物体 |
| 升格 / slow motion / 慢动作 | **静帧或糊片**（官方禁用） |
| 「力的三张回执」/ 发力链 / 重心转移 | 无效果（这是给人看的分析语言） |
| 白闪 / 冲击波环 / 摇臂 / 滑动变焦 | 无效或糊片 |

**只写"看得见的结果"**：手被拉下来、袖口被扯紧、纸从桌上滑落、他往后靠了一下、她抬头。**结果具体到肉眼能核对 → H3 能做；写成行业概念 → 当没看见。**

⚠️ 这条对**外部打戏技能**尤其重要：`sd-combat-engine`（漫剧老李套装，`lixiaoxiao9888-create/manju-laoli-skill`）那套「顿帧／冲击帧三级／白闪／升格」是**给 Seedance 写的**，直接搬到 H3 全部失效。它的**设计层**（IAU 动作单元上限、起爆顿收四拍、双向攻防、抽掉特效能连成武打吗）有价值，**输出层不能抄**。

#### C-3 H3 只演持续接触，不演瞬时发力

| 能演（可靠） | 演不成（会变别的） |
|---|---|
| 抓、揪、拉、拽、按住、扶着 | **推** → 变成"手搭在肩上" |
| 持续接触、僵持、慢慢放下／缓缓抬起 | **打、撞** → 变成静止贴脸 |
| | 快速出拳 → 静帧或糊掉 |

原因：持续接触有稳定的画面状态可渲染；瞬时发力是一个"瞬间"，H3 抓不住那一帧。**肢体冲突要写成"揪住不放"，不是"一拳打过去"。**

⚠️ **2026-11-21 补充实证**：这条不是绝对的。「推」写成物理链（掌心路径→锁骨落点→上身后仰越过髋线→布料堆起→退半步）**实测能推出来**；写成 `pushing into her shoulder` 才退化成搭肩。**所以真正的分界不是「推 vs 抓」，是「有没有写受力方的几何变化」。** 写了就能演，没写就变搭肩。

#### C-4 正文没引用 `<Subject N>` → 那张参考图白挂，模型自己编

**实证**：某段只引用两个人物标签、漏了场景 `<Subject 3>`（办公室）→ 前两段是白板＋百叶窗，这一段的办公室变成木门＋玻璃柜＋显示器＋台灯，**同一间房变成两间房**。

写完每段核对：本段定义的每个 Subject 是否都在正文出现。机检口径 H5「定义了却未被引用（白占 9 图额度）」。

#### C-5 单镜有效动作窗口只有 5-7 秒，超了全是"维持姿势"（2026-11-21 实证）

**症状：片子不报错、动作也对，但大段大段的人不动。** 单看某几帧完全看不出问题，只有连续看才暴露。

实证：57 秒成片（4 段 × 14.3 秒，每段设计 4-5 个动作），全片约 **26 秒人物几乎静止**：

| 段 | 动作做在哪 | 剩多少秒在僵着 |
|---|---|---|
| 01 | 0–7 秒 | **7–14 秒，两人僵在原地 7 秒** |
| 02 | 0–8.6 秒 | **后 4.5 秒站着不动** |
| 03 | 0–8.2 秒 | **后 6 秒手拉手僵着** |
| 04 | 0–5.5 秒 | **后 9 秒一个趴着一个站着不动** |

**结论：一段 = 6-7 秒 = 一个回合（攻 + 挡 + 反击三下）。**

要做 30-60 秒的戏，**拆 6-9 段拼接**，不要靠把单段拉长。拉长的部分不会自动补动作，只会变成静止。

#### C-6 玻璃/镜子/反光面会凭空画出"第三个人"

实测：办公室玻璃隔断里画出了**另一个站着的西装男 + 地上一个白影**，跟前景两人对不上。

修法：要么别放玻璃隔断这类反光面；要么写死 `only a soft blurred reflection on the glass, no distinct human figures`。

#### C-8 一颗塞 3–4 段 + 复用旧参考图 → H3 自己重新导演，人物关系全错（2026-11-22 白跑 3 小时的教训）

**症状**：剧本写的是「咨询师开导来访者，两人隔桌对谈」。出片凡哥一眼看出：**「不像是一个人开导另一个人，之间更像是恋人之间的开导，画面结构是错的啊？你跑出来这个打算干嘛用？」** 另外还有景别乱（写"中景缓推"跑成大特写）、人物在说英文（见 C-7）。

**两个根因，叠加发生**：

| 根因 | 具体 |
|---|---|
| ① **一颗塞 3–4 个切点** | 官方稳定性建议是「5–10 秒、一个主体、一个主动作、**最多 2 个切点**，每多一个切点掉一档」。我塞了 3–4 段，等于让模型在一颗里连换三次导演 → 它自己重排了构图和人物关系 |
| ② **参考图是复用的旧图** | 用的是早先做剪影片时随手生的一张双人对坐图，**从来没按"咨询师 vs 来访者"的关系设计过**。图里没有距离、没有茶几、没有关系，模型只能自己补 → 补成恋人 |

**修法（两条都要）**：

**① 一镜一机位、一刀不切。** 一颗 = 一个机位 = 一个说话人 = 一个节拍，4–9 秒。别为了省时间把三个机位打包进一颗 —— 省下的时间是废片时间。

**② 参考图按本次分镜重新出，三件套齐全：**
- **场景机位图**：正反打各一张（A 机位拍甲过肩、B 机位拍乙过肩）+ 一张双人正面，同一房间
- **人物四视图**：每个角色一张（正面/四分之三/侧面/背面），写死发型、服装、鞋
- **道具图**：一件一张

出图提示词里**必须写死人与人之间的物理关系**（"两人之间隔一张矮茶几"、"他从椅子前沿前倾但不越过桌沿"、"她坐得靠后、肩内收"）。

**判据（以后先过这关）**：凡哥说"关系不对/画面结构错"，**第一反应是查参考图和切点数，不是改提示词措辞**。提示词写得再好，图里没有那层关系、或者模型被切点搞晕了，都救不回来。

**连带**：能执行的镜卡必须写数字，不能写形容词。对照写法 ——

| 项 | 不能写 | 必须写 |
|---|---|---|
| 占框 | "她坐在画面右边" | "她占画高 62%，横坐标 58%，头顶留白约一掌宽" |
| 动作 | "她显得很犹豫" | "手抬起来 → 往门里伸 → 伸到一半停住（手掌摊开、手指微曲）→ 停两秒 → 手指一根根收回 → 攥成拳 → 落回身体两侧" |
| 情绪 | "她很委屈" | "起：手先动了，比脑子快；转：停在半空那两秒是她自己把自己按住；落：攥拳、收回，动作很轻" |

#### C-7 不给音频，H3 自己编台词，口型跟着它编的走（2026-11-22 实证）

**症状**：出片画面都对，但一验音轨发现人物在说**英文**（实测 `"I'll be submitting Faga or Juniating my back to his talk."`），或者是**中文乱码**（`"我想是你我娃的更满意啊"`，其实没人说这句）。凡哥当场质问：**「什么玩意？说的英文？跟我们的内容一样吗？」**

**根因**：H3 是音画同时生成的。**不给参考音频，它就自己编一段语音**，而且语言不可控。**口型跟着它编的那条走** —— 后期配中文全对不上。

**什么时候才露**：中景/远景嘴小、看不清，能混过去；**特写镜必穿帮**（实测 9.4 秒的特写，嘴张着明显在讲英文）。所以**不能靠"景别远一点"来躲**。

**⭐ 正解（2026-11-22 深夜实测跑通，以这条为准）：把台词写进提示词，让 H3 自己生中文语音和对口型。**

```text
[Shot 1] ...; <Subject 1> sits with both hands clasped on her knees.
She says in a low flat voice at an even pace: <d>[Chinese] 我妈说，我弟结婚早。</d>
Her hands stay clasped and the two armchairs stay at the two ends of the table.
```

ASR 回验（faster-whisper large-v3，语言置信度 **1.00 zh**）：
```
0.00-5.30   我妈说,我弟结婚早,钱花得差不多了。
7.18-14.14  她说这话的时候,语气特别平常,就跟说,今天天气不错一样。
```
四句一字不差、全中文、口型跟着中文走。**台词在提示词里，H3 的行为就是「念它给的字」，不会自己编。**

**为什么之前那套 mp3+LoadAudio 不要再当首选**：那是在「台词没进提示词」的前提下打的补丁 —— 补上了口型，但台词内容仍要靠外部音频保证，多一层 mp3 生成、拼句、对齐、掉帧。**台词进 `<d>` 之后这一整层都不需要**。

**次选（仅当必须用外部配音、例如指定真人音色）**：201 节点自身有入口，不用恢复 220/221/226：

```python
api["9100"] = {"class_type": "LoadAudio",
               "inputs": {"audio": "s01_vo.mp3", "upload": "audio"}}
i201["ref_audios.ref_audio_0"] = ["9100", 0]
```

提示词里加 `<Audio 1> is her voice.`，并在 detailed_description 写 `Her lips move in sync with <Audio 1>.`
⚠️ 此路**本次只提交了、未完成验收**（跑完就被更快的 `<d>` 方案取代）。用在正式交付前必须先验一条。

**三条配套纪律**：

- **一句台词一个字也别改**。长句按标点拆成两次开口是允许的（≤15 字一次），**内容一个字都不能动**。
- **拆句之后必须用脚本核对覆盖率**（见下文「拆句后必核台词覆盖」）。
- **语速按 3.3 字/秒算**（`h3_lint.py` 用的就是这个常数），不是 edge-tts 那条 3.7 —— H3 自己念比 TTS 略快。

**四个坑**：

1. **LoadAudio 的节点 id 不能落进 `9001 + i` 的图片区间**（LoadImage 自动按 `9001+i` 编号）。撞上会报：
   `ref_images.ref_image_1, received_type(AUDIO) mismatch input_type(IMAGE)`，`linked_node: ["9002", 0]`。
   **这个报错看着像图片节点配错，实际是音频节点抢了图片的号。** 音频节点用 9100 起。
2. **一句台词一个 mp3**。一镜说好几句，先用 ffmpeg 拼成该镜整条配音：
   `ffmpeg -y -f concat -safe 0 -i list.txt -c:a mp3 shot_vo.mp3`（list.txt 每行 `file 'D:/绝对路径.mp3'`）。
3. **视频秒数可以长于音频**，H3 会走完音频、剩下的时间做表演，不用为了凑音频把分镜改短。
4. **ffmpeg 不认 `/d/` 路径**，`-i` 后面必须写 `D:/...`，否则 `No such file or directory`。

**判定**：台词进 `<d>` 之后不需要再判断这个 —— 只要画面里看得见嘴，就把台词写进去。

#### C-10 拆句之后必须用脚本核对台词覆盖 —— 肉眼和记忆都会漏（2026-11-22 漏 11 句）

**事故**：49 句台词稿，按「一句 ≤15 字 → 长句拆两次开口」重排成 20 段。写完自以为齐了，**用脚本一比：缺 11 句**（正好是全片最狠的那一段）。

**为什么会漏**：把 A、B 两句合并进一段、把 C 句拆成两镜，段号一动，**人对「哪句在哪段」就失去追踪能力了**。记忆会告诉你「写过了」，脚本会告诉你真相。

**核对脚本（每次拆完必跑）**：

```python
import io, re, glob
src = io.open("台词稿.md", encoding="utf-8").read()
orig = [m.strip() for m in re.findall(r"[\"“]([^\"”]+)[\"”]", src) if len(m.strip()) > 1]
got = []
for f in sorted(glob.glob("seg*.txt")):
    got += [x.strip() for x in re.findall(r"<d>\[Chinese\]([^<]+)</d>",
                                          io.open(f, encoding="utf-8").read())]
def norm(s):
    return re.sub(r"[\s，。！？、…‘’“”'\"\-—]", "", s)
blob = norm("".join(got))
miss = [o for o in orig if norm(o) not in blob]
print(f"原稿 {len(orig)} ｜提示词 {len(got)} ｜缺 {len(miss)}")
for m in miss:
    print(" -", m)
```

**读结果的口径**：报出来的「缺」**先分辨是形式差异还是真缺**——拆成两句、去掉引号、省略号换成中文省略号，都会让整句匹配不上但内容在。**逐条回 grep 确认**，别直接当成真缺去补。真缺才是问题。

#### C-11 机检全绿，成片却「脸不动、一个调、哭得突然」——机器查污染，查不出**空缺**（2026-11-23 实证）

**症状**：20 段稿子 `h3_lint` 跑出 **20/20 FAIL 0**，全部合格，交付。凡哥看完只给三句：

> 「人的面部表情」不变 ·「说话的节奏一直不变」·「后面哭得太突然，前面太平」

**硬数据（那 200 秒成片）**：

```
四区动作：眉 0 次 · 眼睑 0 次 · 唇 1 次（还带 a little）· 喉 0 次   ← 她的脸几乎没动过
语调：    says in a low flat voice × 11                          ← 一个调到底，是我自己写死的
停顿：    96% 的句子间隔 <0.3 秒，最长 1.1 秒，3 秒以上停顿 0 次
```

**根因（这是本类最反直觉的一条）**：

> **`H13` 抓的是「你写了『紧张』这种结论词」，抓不到「你什么都没写」。**
> 机器查的是**污染**，查不出**空缺**。全绿 ≠ 演出来了。

技能里 `checklist.md` 的 F 组 5 条，机检列本来就标着 `—`（意思是「机器抓不住，必须人眼过」）——**那五个 `—` 是唯一能拦住这个病的地方，而我没看。**

**复查三问（出片前必过，比机检优先）**：

1. **数四区**：整段（不是整片）眉/眼/口/颌各有几处**可见动作**？有的段是 0 → 那一镜她的脸是死的。写在句子里的「表情安静」「手放膝上」不算，那是姿态不是动作。
2. **数语调**：同一个说法（`low flat` / `even pace` / `slow`）在一段里出现几次？≥2 次 → 这一段没有起伏；全片 ≥3 次 → 全片一个调。
3. **数停顿**：句与句之间有多少次 ≥2 秒的空？一次都没有 → 就是「哭得突然」的成因，情绪没有地方落。

**修法两条（顺序不能反）**：

1. **补机检**：给 `h3_lint` 加 `H37`（某镜四区动作 <2 区 → FAIL）和 `H38`（同段语调重复 → FAIL）。实测校准：旧版一句话式 20 段报 **17 条 FAIL**，加厚版 **0 条**，`H1-H36` 旧结果零变化——说明规则抓得准、不误报。
2. **演出层次按「三拍」拆，中间必须插静止镜**：第 1 拍压住 → 第 2 拍错位裂开 → **中间一个 1–2 秒只写呼吸与眼神的静止镜** → 第 3 拍释放。哭的落点别提前给，前面只到「下眼睑积一层水、不落」。

**同一症状的两种成因，别混**：

| 成因 | 表现 | 修法 |
|---|---|---|
| 一颗塞太多节拍（见上文症状 A） | 写了 9 个表情，脸完全没动 | **拆镜**，一颗一个主节拍 |
| **压根没人写节拍**（本条） | 机检全绿，脸一次没动 | **补四区动作**，每镜 ≥2 区 |

### 验收纪律：单看几帧会误判成"成功"（凡是同类任务都适用）

**血泪教训（2026-11-21）**：一次 57 秒打斗，我只抽了 4 张关键帧就下结论「八拍动作全做出来了、实测成功」——**结论是错的**。把片子压成联系表之后才发现大段静止、动作变成比划、场景中途换了房间。

**正解：压联系表（contact sheet），每 0.5 秒一帧，一段一张。**

```
每段一张 4 列 × N 行的小图网格，每 0.5 秒取一帧，缩小到 320 宽拼起来
```

**看什么（按命中率排序）**：
1. **哪几秒开始两个人都不动了**（→ C-5 动作窗口）
2. **动作是不是变成"比划"**（举手代替出拳、握手代替抓领）
3. **场景有没有中途换**（柜子从书柜变文件柜、窗户位置变了）
4. **段缝接不接得上**（上一段末帧姿势 vs 下一段首帧）
5. **有没有多出来的人/手**（反光面、贴脸缠斗）

**定性判断的标准**：
- **动作对、姿势对、但人物不推进** = 动作密度问题（C-5）
- **人物在动但动作不对** = 写法问题（C-1）
- **动作对但看着假** = 缺受力后果（C-2/C-3）

## 剪影动画短片路线（2026-11-22 跑通，情感内容/解说片通用）

### ① 生图：走快渠道，别用慢的

### ② 剪影提示词的关键词（生图侧）

必须同时写进这几样，否则会画出"半写实照片"：

> 黑白剪影动画风格 / 纯黑剪影 / 无面部细节 / 无身体内部细节 / 背景是透光的窗户 / 逆光把人物勾成剪影 / 极简构图 / 电影感 / 竖构图

⚠️ **必须显式写清人数与性别**（"左男右女、男短发宽肩、女长发窄肩"）。不写就默认画成两个同性别 —— 这就是 B-2「图赢过文字」的源头。

⚠️ **儿童的身体部位要写死比例。** 写"一个小女孩的手悬在半空"，生图画出的是**成年男性的手**（大、指粗、手臂有毛）。要写：`一只七八岁孩子的小手：短、肉乎乎、手指短、没有毛、手臂很细`。不写就按成年人体型渲染。

### ⭐ 纯黑剪影 → 逆光半剪影：情感戏升一档（2026-11-22 同一项目实测对比）

同一份分镜、同一个生图渠道，只改剪影的"黑到什么程度"，情绪强度差很多：

| | 画面 | 结果 |
|---|---|---|
| **纯黑剪影** | 只有轮廓，全黑块，内部零细节 | 一致性完美（没有脸就没有"每颗重骰脸"），但**读不出性别、年龄、关系**；情绪只能靠姿态，说服力弱 |
| **逆光半剪影** ⭐ | 背光，能读出侧脸轮廓、胡茬、发丝、衣褶、针织衫纹理，**五官读不出** | 情感强度明显上一个档；仍然不用守脸的一致性；构图和光变成全部 |

**为什么半剪影不破坏「不用守脸」这个前提**：观众读到的是「轮廓 + 姿态 + 光」，这三样不要求跨镜头一致。
而 H3 最擅长的恰好是光。—— **这是绕开模型弱点的做法，不是硬碰。**

实测：13 颗/20 颗同场景镜头，人物位置、窗户位置、景别稳定，剪在一起不跳；低头、塌肩、长发前滑这些微动作全部成立。

⚠️ 但**景别会漂**：同一张参考图，有的颗出半身、有的颗拉到全身（能看到椅腿地板）。
　 不是失败 —— 剪接时统一裁到同一景别即可，比重新生成便宜。

### 分镜节奏（84 秒片）

### 🔴 对话戏：先算台词秒数，再定颗数 —— 拍脑袋定颗数必返工（2026-11-22 白跑 2 小时）

**上面的「84 秒 12–13 颗」只对"配旁白的意象片"成立。一旦是两个人有来有回的对话戏，颗数必须由台词算出来。**

同一项目第二版：台词稿 49 句、562 字。我按"每颗 10 秒"拍脑袋拆了 20 颗，提交跑了两小时，**排时间轴时才发现只装下 36 句**，剩 13 句（全片最狠那段）没地方放 —— 全废。

```
❌ 先定颗数（"每颗 10 秒 × 20 颗 = 200 秒，够了"）→ 再往里塞台词
   看着够、实际不够：一句台词一出，前 20 颗就装满了

✅ 先算，再拆
   ① 台词总字数 ÷ 语速 = 纯说话秒数 S
   ② 加对话停顿（句间 0.8–1.5 秒；沉默/关键处 2–3 秒）→ 全片长度 T
   ③ 颗数 N = T ÷ 每颗容量（单动作 5–7 秒，见 C-5）
   ④ 反向核对：每一颗里的台词秒数必须 ≤ 这一颗的长度，装不下就拆
```

**实测语速（可直接用）**：

| 音源 | 语速 |
|---|---|
| edge-tts 中文 `zh-CN-XiaoxiaoNeural` / `zh-CN-YunjianNeural`，`rate=-8%`/`-6%` | **3.7 字/秒**（含句内停顿） |
| 我们的真人配音员 | 4.30 字/秒 |

**音色分工（情感对话戏，实测可用）**：
- 当事人（女，克制、疲惫）→ `zh-CN-XiaoxiaoNeural`，`rate=-8%`
- 咨询师/旁问者（男，稳）→ `zh-CN-YunjianNeural`，`rate=-6%`
- ⚠️ `zh-CN-XiaohanNeural` 不存在，调用报 `NoAudioReceived`；`YunxiNeural` 太年轻、`YunyangNeural` 播音腔太重，都不适合情感戏。

⭐ **一句台词 ≈ 一颗镜头**（短句 2–3 秒、长句 5–7 秒，正好落在 C-5 的窗口里）。
　 一句连续说不换气的地方不要拆开——跨两颗会让嘴型在剪点附近反复。
