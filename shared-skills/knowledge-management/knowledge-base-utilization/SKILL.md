# 知识库 / 记忆体系利用率（诊断 · 测量 · 入口）

## When to Use（何时加载）

- 凡哥问「我们知识库能**真正发挥作用**吗」「利用率**高不高**」「要不要配 XX」
- 凡哥说「**吃灰检查**」「哪些东西没人用」「怎么让以后**能想起来翻**」
- 我要给某个资产（知识库目录 / 技能 / 记忆文件）**证明它到底有没有被用过**
- **准备新建**一个知识库目录 / 新资产分类之前 —— 先读本文，别再造一个空壳

## 一、判据：技能是动词，知识库是名词（2026-10-15 凡哥问"哪些该是技能、哪些该是知识库"）

| | 技能 | 知识库 |
|---|---|---|
| 本质 | **怎么做事**（程序性） | **是什么事**（陈述性） |
| 回答 | "遇到 X，我该**怎么做**" | "关于 X，我知道**些什么**" |
| 结构 | 触发词 + 步骤 + 产物 + 验收 | 事实 + 来源 + 日期 |
| 有"失败"吗 | **有**（做错／跑不通／验收不过） | **没有**（只有过时／不准） |
| 谁去读 | 干活时**自动**读 | 需要时**才**查 |

**三问判断法**（逐条过，答不上就换地儿）：

1. 说得出"**什么时候用它**"吗？（触发时机）
2. 它会**让我做得不一样**吗？（改变行为）
3. 它会**过时**吗？（时效）

→ 能改变行为 = **技能**（要能被执行）；只供参考 = **知识库**（要能被查到）。
→ **反用也成立**：一个技能如果**说不清触发词**，它就不该是技能 —— 该并进别的技能，或降级成知识库。

## 二、测量：先解决"怎么证明被用过"（2026-10-15 实测，含一次失败）

### ⛔ atime（最后读取时间）在本机**不可用** —— 别再用

本想用 `atime` 直接测"这个文件最后被读是什么时候"。**实测废掉**：

- `touch -a -d "2026-06-30"` 把 atime 重置后，**1 分钟后再看已被刷成今天**
- **我的体检脚本自己一跑就把全部文件的 atime 刷成"今天"**（40 个文件同时变同一秒）
- 对照实验：`git status` 不变、`read_file` 读完内容也不变，但脚本运行那一刻全变

**根因**：atime 更新是"惰性 + 批量落盘"的，且**观测行为本身会改变观测对象**。
→ **结论：任何"靠读文件来统计读取次数"的方案都会污染数据，一律作废。**

### ✅ 可用指标（两个，互补）

| 指标 | 测什么 | 怎么取 | 可信度 |
|---|---|---|---|
| **mtime** | **有没有人往里写** | `os.stat().st_mtime`（只 stat，**绝不 open 内容**） | 高 |
| **显式使用日志** | **有没有人真的去读** | 路由表里的「使用日志」表，读完记一行 | 中（靠自觉，但有留痕可查） |

- **判据**：mtime 停在同一天的多个目录 = **建完那天就是最后一天**（2026-10-15 实测：30 个库中 14 个**精确停在 2026-06-30**）
- 脚本：`D:\Hermes\scripts\kb_utilization_check.py`（`--baseline` 存基线 / `--diff` 与基线对比；**只 stat 不读内容**，这条铁律写在脚本头里）

## 三、诊断：利用率低 ≠ 内容差，几乎总是**入口缺失**

**2026-10-15 决定性反证**：`director-kb` **6-29 就自带**一张带「触发条件」的路由表（`| 文件 | 触发条件 | 内容 |`）+ 入库铁律 + 完整管线图 —— **照样 107 天没人碰**。

> **局部索引 ≠ 全局入口。** 索引建在库**里面**，干活时根本想不起来翻；做得再好也照样烂掉。

**对照**：技能利用率高，只因为 `skill-router` 路由表的左列全是**场景**（"凡哥说 X"→加载 Y），而不是主题名。人（和 AI）干活时脑子里是**场景**，不是**主题** → 按主题堆的库永远对不上。

**一句话给凡哥**：内容一直在，是"**找得到**"这件事没被设计 —— **书一直在，以前我找不着门**。

## 四、修法：场景→库路由表 + 挂进启动 + 使用日志

### 1. 建一张总入口（照抄 skill-router 的形态）

文件：`D:\Hermes\xiaonan-memory\知识库路由.md`，三部分：

1. **为什么有这张表**（写清"局部索引≠全局入口"的教训，让未来的自己理解它的意义，不只是清单）
2. **场景 → 库**（左列**只写场景**，不写主题名）：

| 什么时候（场景） | 读哪个库 |
|---|---|
| 做短剧选题 / 写剧本 / 想流量 | `video-kb` |
| 设计镜头 / 运镜 / 构图 / 灯光 | `director-kb` |
| 写提示词 / 查模板 | `prompts` + `visual-template-library` |
| 聊 AI 工具 / 选型 / 开源项目 | `open-source-ai-kb`（+ 闭源技巧 `closed-source-ai-kb`） |
| 南溟岛 / 世界观 / 反派 | `world` + `heart-demons` |
| 心理内容 / 副业 | `psychology-kb` + `personal` |
| 凡哥形象 / 穿搭 | `image-kb` + `形象档案` |
| 公司 AI 网关 / 部署 | `tech` |
| 用 Hermes / 装环境 | `tech-kb` + `tutorials` |

3. **使用日志**（读完记一行 = 唯一可信的"读取"证据）

### 2. 挂进 `D:\Hermes\SOUL.md` 启动同步

和 `DASHBOARD.md` **并列**，否则下次开工看不见、等于白建：
> …然后读 `DASHBOARD.md`…；**再读 `知识库路由.md`**（凡哥丢链接/要选题/找资料/聊工具选型前先扫一眼"什么时候→读哪个库"，读完在它里面的「使用日志」记一行；不读=知识库继续当仓库没人翻）。

### 3. 命名坑

`image-kb` 里装的其实是"**凡哥形象/穿搭**"，不是图片素材 —— **名字与内容不符 = 双重找不到**。发现这种库在路由表里**注明真实内容**，并建议改名。

## 五、社区权威实践（2026-10-15 查证，方向一致 + 三条我们还没做的）

来源：Microsoft Copilot Studio 官方文档 / Agent.ai best practices / InfoWorld「Anatomy of an AI agent knowledge base」。

**与我们做法一致**（说明路子没走偏）：
- "**Search the knowledge base first**"（回答前先查，而不是当通用知识答）
- "**Add trigger phrases** matching your knowledge content"（= 场景索引）
- "**Monitor knowledge source usage**"（= 使用日志）

**多出来的三条（下一步可做）**：
1. ⭐ **"Search the KB first" 要写进 system instructions** —— 我们做的是"启动时读一次表"，社区是"**每次回答前强制先搜**"。这是利用率的最大杀招。
2. ⭐ **"Write for AI, not humans"** —— 库内容要按 **AI 检索方式**组织（清晰标题 / 关键词 / 去重去矛盾），不是散文式。
3. ⭐ **"Agents themselves should capture new information and keep the KB up-to-date"** —— **写回要靠 agent 自动**，不能靠人记得；收尾时主动提议入库。

## 六、汇报纪律（凡哥要求：说人话）

- 结论先行，**第一句就是人话**；禁术语 / 英文缩写 / 英文文件名（非说不可时括号里补一句大白话）
- 表格只用于对比，且不超过一屏；**不许拿表格当包装**
- 技术细节只讲**结论 + 对他有什么影响**
- 比喻胜过定义：**技能=贴了标签的活柜子（你会去拿）；知识库=门锁着的仓库（东西在里面，没人翻）**
- 被纠正后**当场把同一结论用人话重说一遍**，比道歉有用

## Pitfalls

1. **别再试 atime** —— 观测即污染，本机已实测废掉（详见 §二）。
2. **别只看 mtime 就说"死了"** —— 维护过 ≠ 用过；低频但必用的资产不能因为"少"就砍。
3. **别只在库内建索引就当修好了** —— `director-kb` 是反例，**必须在启动清单/路由表上挂全局入口**。
4. **路由表左列写场景，不写主题名** —— 写成主题名就退化成第二个"锁着的仓库"。
5. **建了表不挂启动 = 白建** —— 只有进了 `SOUL.md` 启动同步，下一个会话才看得见。
6. **不要求助"下次我记得"** —— 我能落地的只有三样：**文件、启动清单、脚本**。凡是"靠自觉"的机制都要落到能留痕的东西上。
7. 技能侧的吃灰体检（判入口/触发词/实测频次）见 `skill-library-maintenance` §吃灰体检 —— 两侧共用本文的测量方法论。
