## 一、评分制度：全部正向（减分制已撤）

- 凡哥原话①：「减分制只能用在这些"规范动作"上。平台功能、工作流打通、AI 能力接入这类交付活不能用减分制——不然他们会只求不出错、不敢往前冲。**交付用"做到给满分"，规范用"出错才扣分"**。」
- 凡哥原话②（随后改主意）：「**我们还是恢复到原来，只是这个月没有归档的话，就算满分来算**。」
- 最终形态（照这个执行）：
  1. **一套正向评分**：做到给满分，做不到往下走；**不做减分/扣分表**。
  2. **归档项：本月没有归档事项 → 直接算满分**（不考核这一项）。
  3. 交付类（平台功能 / 工作流打通 / AI 能力接入）**永远不用减分或倒扣**。
- 归档项正向档位：换人照着能用 **100** ／缺小步骤 **80** ／缺关键步骤或迟交 3 天内 **60** ／迟交超 3 天 **40** ／没交 **0**。

## 二、凡哥原则：不为了打分而增加记录动作

- 凡哥原话：「跟工作结果没有太大关系的没有必要去设计，反而**增加工作量和精力**。」
- 落地：**验收只看产物**（当场点页面／并排看设计稿／走一遍主流程），**不要求员工额外写记录**。
- 本次按此删/改掉的项（**别再往表里加回来**）：
  - **走查记录**（UI）→ 删。原写法"走查通过、问题 ≤3 项"改成"**当场点页面 + 并排看设计稿**"。
  - **出片案例** → 删（凡哥原话：「**出片案例是别人去试，不是他来试**」），小何的"数据"类改用**反馈台账**。
  - **故障修复记录 + 维护迭代记录** → **合并**为一条「**故障与维护记录**」。

## 三、归档规则

### 3.1 项目结束的定义（凡哥定）
**正式部署到服务器、并正式可以使用 = 项目结束**；之后只有维护和迭代。
→ 推论：OPC 平台"第一版可演示"**不算结束**，不触发正式归档。

### 3.2 四个触发点
| 触发点 | 交什么 | 时限 | 谁写 |
|---|---|---|---|
| ① 日常 | 工作日志（每天）+ 一句话进展 | 持续 | 本人 |
| ② **阶段里程碑**（可演示／第一阶段验收） | **阶段小结**（过程留档，**不叫正式归档**） | 里程碑后 3 天内 | 本人 |
| ③ **项目结束**（正式部署可用） | **《项目归档文档》**（设计／如何落地／说明） | 上线可用后 **3 个工作日** | 设计＝前端+UI；落地+说明＝后端 |
| ④ **之后每次维护与迭代** | 《维护与迭代记录》**加一行** | 改完**当天** | 执行人 |

> 为什么②必须有：③ 那一刻大家赶上线、最累，**最容易糊弄**；② 先把原料攒起来，③ 到点只是"拼起来"。

### 3.3 《项目归档文档》三段（读者＝接手的人，不是自己）
1. **设计**：做什么、给谁用、范围（包括什么／**不包括什么**）、关键决定与原因、界面/交互稿在哪
2. **如何落地**：用了什么工具/平台、**完整步骤（细到别人照着能走一遍）**、关键参数（**写具体数值**）、素材路径、分工、耗时与踩过的坑（原样记，别美化）
3. **说明**：怎么用、注意什么（禁忌/易错点）、**未解决的问题（诚实写）**、谁维护、相关文件清单

### 3.4 验收铁标准（一句话）
**换一个没参与的人，照「如何落地」能不能独立走一遍？** 能 ✅ ／不能 ❌（退回重写）

### 3.5 三种常见写错（提前拦住）
| ❌ 这么写 | ✅ 该这么写 |
|---|---|
| "流程已打通" | "① 打开 X ② 导入 Y ③ 设 Z=8 ④ 导出到 W 目录" |
| "参数按需调整" | "步数 8、CFG 3、分辨率 1920×1080" |
| "后续会优化" | "现在问题是 A、B，思路是 C，计划 X 月做" |

## 四、月度任务台账（工作内容是浮动时的考核底盘）

**凡哥的问题（原话）**：工作安排不是月初月末才加，**随时都会增加工作内容**；月度考核应该**先列举本月有哪些项目、什么时候下发、预计什么时候交付，然后才是实际交付、卡点，再在交付过程里考核**。

**机制：下发即登记的任务台账**
文件：`D:\Documents\我的文档\CTO攻略\月度任务台账_模板.xlsx`
字段：序号｜项目｜任务内容｜**下发日期**｜**承诺交付日**｜**实际交付日**｜状态｜改期次数｜卡点/原因｜负责人

**六条规则**：
1. 随时加行（**下发即登记**，5 秒的事）
2. 中途加的活**当场定交期**（不能"加了活还不给时间"）
3. 改期留痕（谁改／为什么／改到哪天），但**改期不直接扣分**——**改期次数是辅导点，不是罚点**
4. 本月未完成**滚下月标"跨月"**，不消失
5. 月底**冻结：只统计不新增**
6. 考核只数两个数：**按时交付率** ＋ **卡点处理情况**

**为什么站得住**：这就是 CEO 那套「执行人报时间 → 盯时间 → 到点要结果 → 总结卡点 → 开下一轮」的**表格化**；也是"承诺 vs 交付"的可数化。
**一份表三用**：HR 日志原料 ＋ 月度考核数据 ＋ 给 CEO 的一页纸周报 → **不额外增加记录动作**（守住 §二 的原则）。
**谁维护**：执行人各自填自己的行（承诺日期他填、实际交付验收后填）；CTO 只做两件事——**派活、验收**。

## 五、考核三支柱（凡哥定：按 流程／资产／数据 考）

| 支柱 | 后端（整体框架+后端） | 前端＋UI |
|---|---|---|
| **流程** | 框架搭建、工作流打通、Agent/生成能力接入 | 前端页面实现、与后端联调打通 |
| **资产** | 工作流 JSON、接口文档、后端模块沉淀 | 设计稿、设计规范、前端组件库 |
| **数据** | 反馈台账、**故障与维护记录**（已合并）、交付记录 | 页面交付记录、改稿记录 |

**每人三类各至少一条考核项** → "沉淀"这才不再是空话。
⚠️ 已删：走查记录、出片案例（见 §二）。

**战略含义（凡哥认同）**：公司是「**壳 + AI**」模式——给 AI／智能体搭外壳，按需求扩展功能，**不自研算法、不自研模型**。
→ 所以 KPI 里不该出现"核心算法实现"这类词（应写 **「Agent 能力接入与跑通」**）；**值钱的不在算法，在 ①壳里的流程 ②攒下来的资产 ③数据** —— CTO 的技术护城河只能建在这三样上。

## 六、在对方（人事）的表上标记"建议改动"的做法

只口头列一串"我改了哪几处"容易说不清；用 openpyxl `Comment` **在你建议改的单元格上挂批注**，对方一眼就能分清哪些是建议、哪些是她原文：

```python
from openpyxl.comments import Comment
ws['C7'].comment = Comment('小南建议：原表三项权重 30+30+20 合计仅 80%，建议改 40/40/20，请 HR 确认', '小南')
ws['D7'].comment = Comment('小南建议：按"整体框架 + 后端"的实际工作改写原 KPI 描述，请确认', '小南')
```

- 批注只挂在**你建议改动**的格：KPI 描述（D 列）改写处、权重调整处。
- 正文写入仍只碰**业务列**（E 评分标准、D KPI 描述），格式/公式/合并单元格一律不动（见 `references/KPI按实际工作设计.md` §二）。
