# 「AI 数字员工」到底是什么 · 现成开源方案（2026-11-22 调研，未实测部署）

## 一、先给需求命名：他要的不是「五项功能」，是「一个替主管干杂事的 AI 助理」

凡哥当时的状态：小唐做「AI 数字员工五项」，五天全砸在第①项（报销排版打印），其余四项零记录；
凡哥自己的话是「**我对数字员工毫无头绪**」，小唐「**很迷茫**」。

**根因不是人不行，是这件东西没有名字、也没有品类参照** —— 一旦知道它叫什么，市场上早有成熟实现，
就不该从零写。

**它叫什么**：AI 数字员工平台 / AI Employee Platform / Digital Employee。
形态＝给 AI 配「岗位 + 技能 + 工具 + 知识库 + 通道（IM）」，让它自己去取数据、产文件、发消息、按时间自动跑。

对照五项：① 报销排版打印＝一个技能；② 自写日报＝定时任务 + 技能；③ 月底考核表＝吃前面数据的技能；
④ 下发任务＝IM 通道 + 写表；⑤ 日历可视化＝读项目节点的视图。
**五项＝一个员工的五个技能，不是五个系统。**

## 三、为什么首选 UniEmployee（四条，按重要性）

1. **许可＝MIT**：openvort / StaffDeck 是 AGPL-3.0。**内部自用没事，但一旦做进诺境的产品对外提供服务，
   开源义务会跟到产品上。若要卖给客户 → 只能选 MIT。** 这一条现在不提，以后要拆。
2. **技能格式＝`SKILL.md` ＋ frontmatter —— 和我们自己的技能库同构**。
   它的五层是 `Employee → Workflow/SOP → Skill(SKILL.md) → Connector(MCP) → Tool`。
   意味着**我们现成的技能（考核、日报、分镜、采购）可以直接变成数字员工的技能**，不用重写。
3. **飞书通道可配置 + 支持 RAGFlow**（小唐已经在用 ragflow）。
4. **cron / webhook 自动任务 + 审批 + Trace** —— 正好补上凡哥要的「可审批、可观测」。

它的内置员工样例也能看出形态：`hrbp`（HR 合作伙伴）、`xiaoshu`（数据分析）、`xiaoxiao`（客户经理）、
`market-intel`（市场情报）——**一个员工＝人设＋模型＋技能＋工具＋知识库＋连接器**。

## 四、落地路径（三天能出一条真链）

1. **装**：Docker 一键起（`docker compose up -d`，含 PostgreSQL）
2. **接飞书**：企业自建应用通道凭据（**权限是小唐的卡点也是他的优势 —— 他已是飞书后台管理员**）
3. **配一个「日报员」**：技能写成 SKILL.md，输入＝他们每天写的飞书日报，输出＝周报/月报
4. **用真数据验证**：拿当月真日报跑一遍，跟手工汇总对一遍

⚠️ **卡点不在技术，在飞书读权限**（读日报 / 读审批 / 发消息）。权限不通，平台装了也是空转。

## 六、检索方法（下次复查用同一条路）

```bash
# ① 仓库硬数据（stars/license/pushed_at/language/description）
curl -s --max-time 30 https://api.github.com/repos/<owner>/<repo>

# ② README 正文（判断是否支持飞书、有哪些模块、怎么部署）
curl -s --max-time 30 -H "Accept: application/vnd.github.raw" \
     https://api.github.com/repos/<owner>/<repo>/readme
```

注意：`raw.githubusercontent.com` 在本机常 DNS 失败（curl exit 6），**`api.github.com` 通**，
所以一律走 API；抓 README 用 `Accept: application/vnd.github.raw` 直接拿原文。

## 七、给下属派这件活的口径

**不要派「做五项功能」**（没有边界 → 只会往唯一有产物形态的那项上钻）。
派「**装一个平台，配一个员工，跑通一件事**」，并给每个技能一句外行能判的验收标准。
